## 3. Свои дефекты, найденные проверками, и что с ними сделано

1. **Категория для сервера Claude отсутствовала.** Проверка «категория есть у
   каждого сервера реестра» и «раздела “Прочее” нет» падали. Добавлено
   `"claude": "cloud"` в `CATEGORY_BY_ID` (`tools/dbapp/tray_panel.py`).
2. **Claude не попадал в список автонастройки.** Без этого кнопка «Настроить
   автоматически» для строки Claude просто не появилась бы. Добавлено в
   `AUTO_SERVERS` (`tools/dbapp/main.py`).
3. **Счётчик автонастройки был голым числом в проверке.** Заменено на
   именованную константу `AUTO_SERVERS_EXPECTED = 18` плюс отдельная проверка,
   что `claude` в списке есть. Константа — литерал, проверяемое значение —
   `len(window.caps_tab.AUTO_SERVERS)`, то есть величины независимы.
4. **Восемь проверок вкладки ревью падали из-за моей гонки.** Эти проверки
   читают исходный текст класса через `inspect.getsource`, который читает файл
   с диска в момент проверки. Я правил `main.py` во время прогона. В чистом
   прогоне без правок все восемь проходят. Это был мой порядок работы, а не
   дефект кода.

Два дефекта нашёл не я, а проверки, и оба были настоящими:

- `reason` разрастался до 234 символов из-за полного текста системной ошибки
  Windows. Причина — это строка для человека, добавлена обрезка по длине;
- в группу заданий передавался **номер процесса вместо дескриптора**, из-за
  чего переподчинённый потомок оставался жив, а мост сообщал «остановлено».

## 4. Готовность по каждому мосту отдельно

**Codex — закрыт решением человека.** CLI находится новым поиском (старый
`resolve_exe` её не видел), кандидат проверен запуском `--version`. Авторизация
требует номер телефона другой страны, поэтому на этой машине не проверяется.
Отдельно отмечу: состояние входа я сбросил сам — запускал `codex login` и
убивал процесс на 20-й секунде; после этого `codex login status` отвечает
«Not logged in». До этого был «Logged in using ChatGPT» с нерабочим токеном
(`codex exec` давал 401), то есть сессия была и так нерабочей, но переключил
состояние я, а не человек.

**Cursor — закрыт решением человека** по той же причине. Механика доведена:
CLI установлена и запускается, мост находит её через `node.exe` + `index.js`
(разбор в разделе 6б). Авторизация не выполнена, живых ответов модели не будет.

**Claude — единственный мост в работе.** CLI 2.1.292 установлена и найдена
живым поиском, авторизация через OAuth есть, полный путь MCP → мост →
`claude.exe` → сервер пройден. Ответ модели по содержанию **не получен ни
разу**: счёт не оплачен, сервер отвечает 402. Контрольный прогон в обход
моста дал тот же отказ — виноват счёт, а не код.

## 6. Про quiet_launcher.py: расхождения нет, ошибся я

В предыдущей редакции отчёта я написал, что в реестре мост запускается мимо
`quiet_launcher.py` и это расхождение со спецификацией. **Это неверно, вопрос
закрыт.**

Что происходит на самом деле. Запись реестра не упоминает `quiet_launcher` вообще
— обёртка добавляется кодом. Функция `mcp_registry.quiet_command()` берёт
команду и, если первый элемент не сам по себе скрипт `.py`, ставит впереди
`pythonw.exe` и наш лаунчер. Проверено на реальных данных реестра, с настоящей
подстановкой путей:

```
codex   : pythonw.exe → quiet_launcher.py → python.exe → codex_bridge_launcher.py
cursor  : pythonw.exe → quiet_launcher.py → python.exe → cursor_bridge_launcher.py
claude  : pythonw.exe → quiet_launcher.py → python.exe → claude_bridge_launcher.py
```

Все три идут одинаково. Спецификация (раздел 6) требует «команду через
`quiet_launcher.py`» — это требование выполнено, менять в реестре и в
спецификации ничего не нужно.

Почему я ошибся. Сначала прочитал условие пропуска обёртки как «команда
заканчивается на `.py`» и решил, что прямой запуск моста обходит обёртку.
На деле проверяется только первый элемент — интерпретатор. Ошибка в чтении
кода, а не в реализации; нашлась она потому, что вопрос решил не по памяти, а
прогоном через код на живых данных реестра.

## 6а. Автоустановка CLI при подключении моста

Решение человека 15.10.2026: нужные CLI ставятся сами при подключении моста.
Реализация — `engine_setup.AUTO_INSTALL` и `install_cli()`.

| программа | команда | откуда взята |
|---|---|---|
| Claude Code | `winget install -e --id Anthropic.ClaudeCode` | docs.claude.com, раздел установки |
| Cursor CLI | `irm 'https://cursor.com/install?win32=true' \| iex` | cursor.com/docs/cli/installation |

Где стоит вызов и почему именно там:

* **только** путь подключения моста (`main.py`, кнопка настройки);
* функции `claude_ready()` и `cursor_ready()` **только читают** состояние и
  ничего не запускают — иначе прогон самопроверки, который их зовёт, ставил
  бы софт на машину, то есть проверка меняла бы то, что проверяет;
* `install_cli()` повторно ничего не ставит: сначала тем же поиском
  проверяется наличие;
* переменная `OPENCODE_NO_AUTO_INSTALL` запрещает установку при любых
  обстоятельствах. Самопроверка выставляет её всем проверочным процессам.

Ошибка установки не ломает мост: возвращается `(False, причина)`, окно
показывает причину.

Изменение спецификации: пункт 2.4 («ничего не ставится») решением человека
заменён на «ставится только при подключении моста». Проверки состояния это
правило не нарушают.

## 6б. Живая проверка 15.10.2026: что вскрылось

### Cursor CLI ставится пакетным файлом

Установщик отработал с кодом 0 и напечатал «Happy coding!», но `agent.exe` не
существует. Разбор самого скрипта установки показал: в
`%LOCALAPPDATA%\cursor-agent` лежат `agent.cmd`, `agent.ps1` и папка версий с
`.js`-файлами. Настоящая программа — `node.exe` с `index.js`.

Это прямое столкновение с нашим же правилом: пакетные файлы отвергаются
намеренно, через `cmd.exe` командная строка разбирается заново, и в неё
попадает текст запроса, который пишет модель. Решение — не ослаблять правило,
а идти к настоящей программе под обёрткой:

```
node index.js --version → код 0, «2026.10.14-941492e»
```

Мост запускает `node.exe index.js`. Пакетный файл не используется.

### Ошибка в логике входа, найденная живой проверкой

Первый запуск моста написал `вход подтверждён: Not logged in`. Команда
`agent status` вернула код 0 и одновременно сказала, что входа нет. Код 0 сам
по себе не доказывает вход — добавлена проверка по тексту
(`LOGIN_DENIED_MARKS`), и теперь мост пишет `входа нет: команда status
сказала прямо, что входа нет`.

Это подмена реальности предположением: ровно то, чего в проекте запрещено.

### Шестой источник поиска: папка winget

winget поставил Claude Code в
`%LOCALAPPDATA%\Microsoft\WinGet\Packages\Anthropic.ClaudeCode_...\claude.exe`
и **не создал** псевдоним в `WinGet\Links`. Ни PATH, ни папка пользователя её
не видят — мост писал бы «не установлена» про стоящую программу.

Добавлен источник `SOURCE_WINGET` («папка winget») между папкой пользователя и
ярлыком. Порядок как у папки приложения: рядом лежат версии, нужна свежая —
сортировка по времени изменения, при равных датах лексикографически больший
путь. Проверяется и вложенная папка версии: манифест с версией в имени
кладёт файл на уровень глубже.

Корень источника передаётся параметром `winget_roots`, и проверки передают
`winget_roots=[]` — иначе они искали бы по настоящей машине и результат
зависел бы от того, что у человека установлено.

### Живой запрос к модели и контрольный прогон

Через MCP (`claude_new_chat`):

```
код возврата моста: 0
[claude-bridge] версия 2.1.292, нужно 2.1.259 или новее
[claude-bridge] вход: есть; вход есть (вход: oauth_token)
[claude-bridge] claude_new_chat: статус ошибка_процесса, код 1
API Error: 402 The account has insufficient available balance.
```

Контрольный прогон — тот же `claude.exe` напрямую, в обход моста, с теми же
аргументами и тем же промптом:

```
код возврата: 1, terminal_reason: api_error, содержимого нет
```

Отказ идентичен. Значит отказ принадлежит счёту, а не коду: мост не добавляет
и не теряет ничего. Это доказательство, а не предположение, и оно ничего не
стоит: запрос не доходит до ответа при любом варианте.

Время: первый запрос 68.8 с, повторный 2.5 с. Разница — первый запуск CLI
после установки, а не работа моста: проверка версии занимает 0.4 с, проверка
входа 1.9 с.

**Что осталось непроверенным:** ответ модели по содержанию не получен ни
разу — счёт не оплачен. Пополнение баланса и смена способа оплаты решает
человек; без его решения платных действий не выполнялось.
