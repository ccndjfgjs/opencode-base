# _исходники-батников — тексты батников для правок

Батник лежит в корне базы и **не предназначен для правки напрямую**: в нём
переводы строк Windows (CRLF), из-за чего редакторы могут его портить. Правим
исходник здесь, потом пересобираем файл командой.

| Исходник | Готовый файл (в корне базы) |
|----------|------------------------------|
| `База.исходник.txt` | `База.bat` — **единственный батник базы, с главным меню** |

## Единый батник «База.bat»

Собирает в себе всё, что делали три прежних батника, и запускается одним
двойным щелчком. Главное меню:

| Пункт | Что делает |
|-------|------------|
| 1 | Развернуть базу на этом компьютере (проверка Node.js + `tools\deploy.js`) |
| 2 | Восстановить конфигурацию OpenCode из папки `config` |
| 3 | Импорт базы и скиллов в другую программу (подменю на 7 программ + проверка всех) |
| 0 | Выход |

Ключи: `/y` — не задавать вопросов; `--selftest` — только проверка, без записи;
`--import:<id>` — импорт в программу без меню, только для проверок
(например `--import:codex`). Разделитель — двоеточие: знак `=` в аргументах
режется некоторыми оболочками (проверено на Git Bash).

## Куда при импорте кладутся скиллы

Импорт (пункт 3) переносит не только файлы базы, но и папку `skills` —
все 9 скиллов. Куда именно они попадут, батник ищет по порядку:

1. папка `skills` рядом с папкой найденной программы — это её законное место;
2. если рядом нет — стандартное место **только той программы**, в которую
   идёт импорт (`.codex\skills`, `.claude\skills`, `.dsh\skills` и т.д.);
3. если и его нет — папка создаётся, и батник пишет предупреждение,
   что место подобрано по догадке.

Служебные папки npm (`AppData\Roaming\npm`) для скиллов **не используются** —
там лежат установленные пакеты, а не настройки программы. Если программа
найдена только по команде (например `dsh`), батник всё равно положит скиллы
в её папку настроек.

Прежние скиллы в папке назначения не удаляются: `robocopy /e` только
добавляет и обновляет. Проверено на практике: чужой скилл `МОЙ-ЧУЖОЙ-СКИЛЛ`
в папке назначения остался на месте.

В конце каждого импорта батник печатает **полный путь**, куда легли скиллы —
чтобы это не приходилось угадывать.

### Qwen — единственная программа, которой скиллы не переносятся

Qwen — **оконное приложение**, а не консольная программа. Папку `skills` оно
не читает вообще: она лежит в его папке мёртвым грузом. Проверено разбором
файла `resources\app.asar` — в коде приложения нет ни одного упоминания
скиллов. Файлы базы Qwen тоже не использует (он не подхватывает `AGENTS.md`).

Поэтому батник для Qwen:

- в подменю стоит с пометкой «оконное приложение, скиллы работать не будут»;
- перед импортом печатает честное предупреждение;
- шаг скиллов пропускает и говорит, что они остались в базе;
- в итоге пишет «файлы базы импортированы», без слов про скиллы.

Прежние отдельные батники (`Развернуть-базу.bat`, `Восстановить-opencode.bat`,
`Импорт-базы.bat`) **удалены 16.09.2026** — их функции полностью вошли в
`База.bat`. Копия удалённых файлов вместе с исходниками лежит в архиве
`.workbuddy-ai/backups/batniki-pered-udaleniem-2026-09-16.tar.gz`.
Если их когда-нибудь понадобится вернуть — распаковать архив в корень базы.

### Защита от служебной папки npm

Отдельная засада: команда `where dsh` для программ, поставленных через npm,
возвращает папку **самого пакета** — `AppData\Roaming\npm`, а не папку
настроек. Если взять её как папку назначения, файлы базы уедут в папку
установленных пакетов (так и случилось 16.09.2026 — база разлилась
по `AppData\Roaming\npm`).

Теперь и `:do_common`, и `:do_opencode` проверяют **последнюю папку пути**:
если это `npm` или `node_modules`, подпрограмма `:fix_npm_config` заменяет
её на настоящее место настроек программы и печатает, что было и что стало:

```
   ПОПРАВКА: выбрана служебная папка npm
   Было:  C:\Users\...\AppData\Roaming\npm
   Стало: C:\Users\...\.dsh
```

Сравнивать полный путь нельзя — значение `where` и путь песочницы не совпадают
дословно, поэтому проверяем только имя последней папки. Лишние файлы из
`AppData\Roaming\npm` удалены, копия — в архиве
`.workbuddy-ai/backups/npm-lishnee-2026-09-16.tar.gz` (84 файла).
Сами пакеты (`dsh*`, `opencode*`, `pnpm*`, `node_modules/`) не тронуты.

## Как пересобрать (из Git Bash)

```bash
cd "{{BASE}}"

# единый батник с главным меню
sed 's/$/\r/' "_исходники-батников/База.исходник.txt" > "База.bat"
```

`sed` добавляет в конец каждой строки `\r` — так получаются переводы строк Windows.

## Обязательно проверять сборку

Если конвертация обрывается на середине, батник получается **обрезанным** —
он запустится, но будет вести себя странно (например, «метка не найдена»).
Поэтому после сборки сравниваем число строк:

```bash
src=$(wc -l < "_исходники-батников/База.исходник.txt")
bat=$(grep -c "" "База.bat")
echo "исходник: $src, батник: $bat"   # числа должны совпасть
```

Надёжнее сверять не только число строк, но и всё содержимое — так обрезка
или незамеченное искажение видны сразу:

```bash
cmp <(tr -d '\r' < "База.bat") "_исходники-батников/База.исходник.txt" \
  && echo "СОДЕРЖИМОЕ ИДЕНТИЧНО"
```

## Правила безопасного батника (найдено на практике 15.09.2026)

При написании батников накопились ошибки, которые стоит
помнить при правке **любого** батника:

1. **Скобки `(` `)` внутри блока `if ( ... )`** в тексте `echo` cmd принимает
   за конец блока и падает с «`. was unexpected at this time`». Внутри блоков
   либо не писать скобки, либо экранировать их: `^(` и `^)`.
2. **Кириллица в сравнениях внутри блока `if`** сравнивается по-разному в
   зависимости от кодовой страницы, из-за чего проверка может «проскочить».
   Для служебных `if` использовать латиницу (`Y`/`N`, `yes`/`no`).
3. **`set /p "ПЕРЕМ=текст: "`** — двоеточие перед закрывающей кавычкой ломает
   разбор. Кавычку закрывать сразу после текста.
4. **`set /a СЧЁТЧИК+=1` с `%ПЕРЕМЕННАЯ%`** внутри блока не срабатывает —
   нужны восклицательные знаки `!ПЕРЕМЕННАЯ!` (включён `EnableDelayedExpansion`).
   Надёжнее вынести печать и счётчики в отдельную подпрограмму `:метка`.
5. **Склейка путей:** `%ПАПКА%имя` склеивается без разделителя, если у
   переменной нет обратного слэша на конце (`C:\sandbox` + `fake` =
   `C:\sandboxfake`). Писать `%ПАПКА%\имя`.
6. **Имена программ для меню** (например, «Cloud — Claude») задавать
   **до** вызова `call :probe`, иначе в списке будет пустое имя:
   внутри `call` отложенное раскрытие переменной, по которой строится имя
   подпрограммы, не срабатывает.
7. **`if errorlevel 1` сразу после перенаправления** (`> "файл" echo текст`)
   срабатывает ложно. Надёжнее проверять сам факт создания файла:
   `if exist "файл" (…) else (…)`.
8. **Папку назначения создавать заранее и проверять результат.** Без этого
   `copy` и `robocopy` молча проваливаются, а в отчёте появляются «ОШИБКА»
   без объяснения причины.
9. **Два `if ( … )` один внутри другого — cmd падает** с «set was unexpected
   at this time». Особенно если внутри идёт разбор аргумента. Заменять на
   переходы по меткам (`if … goto :метка`), без вложенных блоков.
10. **Срез пустого аргумента даёт мусор.** У `%~1`, которого нет,
    конструкция `%ARG1:~0,8%` выдаёт строку «~0,8», и любая проверка
    с ней ломается. Перед срезом всегда проверять, что аргумент не пуст.
11. **Проверять запуск ДВОЙНЫМ ЩЕЛЧКОМ, а не только с ключами.** Именно
    при запуске без аргументов вылезают ошибки вида «set was unexpected
    at this time» и «метка не найдена». Так было 16.09.2026: батник
    отлично работал с `--selftest`, но не открывался у пользователя.
    Проверка: `./База.bat < /dev/null` из Git Bash — вывод должен начинаться
    с меню, без слова «unexpected».
12. **После подмены папки назначения проверять, что она непустая.**
    Если подпрограмма замены не смогла подобрать путь, `CONFIG` может
    оказаться пустым — и тогда `copy` или `robocopy` без папки назначения
    скопирует файлы куда угодно. После каждой такой замены ставить
    `if not defined CONFIG goto :eof` и только потом работать с папкой.
    Так сделано в `:do_common` после вызова `:fix_npm_config`.

## Как проверять батник, не рискуя своими папками

Полноценно протестировать батник можно **без записи в реальные папки**:
скопировать базу и подменить домашние пути в отдельном тестовом файле-обёртке:

```bat
set "USERPROFILE=D:\проверка\fake"
set "APPDATA=D:\проверка\fake\AppData\Roaming"
set "LOCALAPPDATA=D:\проверка\fake\AppData\Local"
call "D:\проверка\база\База.bat" --import:codex
```

Ключ `--import:<id>` выполняет импорт сразу, без меню и без вопросов —
именно так проверяются все семь программ. **Важно:** подменять
`USERPROFILE` недостаточно — команда `where` всё равно вернёт настоящий
путь установленной программы. Поэтому для проверки лучше создавать
папку настроек внутри `fake` (тогда батник найдёт её и в `where` не пойдёт).

Тогда все копирования уйдут в папку `fake`, а настоящие настройки не
пострадают. **Без такой подмены запускать импорт на проверку нельзя** —
он реально пишет в папки программ.

Проверено на практике: у `dsh` (Harness) команда `where` возвращает
настоящий `AppData\Roaming\npm`, даже когда `USERPROFILE` подменён.
Именно поэтому скиллы не кладутся в папки npm — иначе они уехали бы
в служебную папку пакетов. Начиная с 16.09.2026 то же правило действует
и для самих файлов базы: папка `npm` распознаётся и заменяется
на `.dsh` (см. «Защита от служебной папки npm» выше).

**Ещё одна ловушка этой же проверки:** `set /p` не читает данные из конвейера,
поэтому запуск батника в песочнице похож на работу, но пункты меню выбрать
нельзя. При этом сам батник после ввода пустой строки бесконечно возвращается
в меню — вывод растёт на сотни килобайт. Это **не ошибка батника**, а признак
того, что ввод пустой; для проверки на ошибки синтаксиса достаточно первых
двух килобайт вывода.

## Почему кодировка именно UTF-8

Батник начинается строками:

```bat
@echo off
chcp 65001 >nul
```

`chcp 65001` включает кодовую страницу UTF-8. Благодаря этому:

- русский текст в батнике и **вывод Node.js** (он всегда UTF-8) отображаются
  одинаково правильно — раньше вывод Node превращался в кракозябры;
- в тексте допустимы любые символы (длинное тире «—», кавычки «ёлочки» и т.п.).

**Так было не всегда, и это стоило ошибки.** Раньше батники хранились в CP866
(кодовая страница консоли), и текст собирался командой `iconv -f UTF-8 -t CP866`.
Проблема: в CP866 нет символа «—», и `iconv` при встрече с ним **молча обрывал
конвертацию** — файл получался обрезанным ровно на этом месте. Внешне всё
выглядело собранным, а батник терял половину кода и писал «метка не найдена».

Поэтому: UTF-8 без `iconv`, и всегда сверяем число строк.

## Важно: `set /p` и пайпы

`set /p` (ввод пункта меню) **не читает данные из конвейера** — если запустить
батник как `echo 1 | База.bat`, меню прокрутится в цикле и выбор не сработает.
Поэтому меню проверяется только запуском окна `cmd` вручную, а отдельные
подпрограммы — запуском батника напрямую с ключом `--selftest`.
