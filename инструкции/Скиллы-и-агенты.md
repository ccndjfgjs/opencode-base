# Скиллы, агенты и «результат не устроил»

Этот файл подключается к **каждой** сессии автоматически, поэтому
инструкции ниже действуют всегда, пока подключена эта база.

Он отвечает на три вопроса:

1. **Какой скилл взять** под текущую задачу.
2. **Какого агента позвать**, если скилла мало.
3. **Что делать, если результат не устроил** — самый важный раздел, он в
   конце.

Подробный список скиллов с условиями срабатывания лежит в
`skills-index.json` (поля `when` — когда применять, `trigger` — по каким
словам понять, что пора, `result` — что получится). Этот файл — короткая
рабочая шпаргалка, а не копия того файла.

---

## 1. Порядок в начале работы

Прежде чем что-то делать, по порядку:

1. Прочитать `библиотека/АКТИВНАЯ-ПАМЯТЬ.md` — на чём остановились.
2. Прочитать `facts.md` — правила и запреты этого пользователя.
3. Если работаем в проекте — `projects/<Проект>/_проект.md`.
4. **Выбрать скилл под задачу** (раздел 2). Скилл берётся **до** начала
   работы, а не после.
5. Понять, нужен ли агент (раздел 3).

Пропуск шага 4 — самая частая ошибка: задача сделана «на автомате»,
существующий скилл не использован, и результат хуже, чем мог бы быть.

## 2. Как выбрать скилл

| Задача | Скилл |
|---|---|
| Нужно создать или изменить, но детали ещё не обсуждали | `brainstorming` |
| Есть спецификация или требования, нужен пошаговый план | `writing-plans` |
| План уже есть, надо выполнить его по шагам | `executing-plans` |
| Новая функция или исправление бага | `test-driven-development` |
| Баг, упавший тест, «раньше работало, теперь нет» | `systematic-debugging` |
| Хочется сказать «сделано», а доказательств нет | `verification-before-completion` |
| Работа закончена, надо показать результат | `visual-report` |
| Интерфейс, веб-страница, окно программы, дизайн | `frontend-design` |
| Картинка, постер, `.png` или `.pdf` | `canvas-design` |
| Сценарий: видео, ролик, презентация, игра | `scriptwriting` |
| Любая работа с картами, метками, маршрутами | `geo-map-compliance-guard` |
| Создать новый навык или починить старый | `skill-creator` |
| Знакомство с пользователем, заполнить профиль | `user-onboarding` |
| Инженерная работа в неформальном стиле | `pohuy` |
| Ответ в стиле сталкера | `stalker-voice`, `stalker-roleplay` |
| Загрузка памяти базы в сессию | `auto-memory-load` |

Правила выбора:

- **Один скилл — одна задача.** Если задача подходит под две строки
  таблицы, это разные задачи: сделать по очереди, а не смешивать.
- **Не вызывать скилл «для галочки».** Если задача не подходит ни под одну
  строку — работать без него и честно сказать об этом.
- **Скилл выбирается до правок.** После того как код уже написан,
  подключать `brainstorming` поздно.

## 3. Как выбрать агента

Агент — это отдельная «голова» со своей ролью. Вызов: `@имя` в чате.

| Задача | Агент |
|---|---|
| Найти, где в коде нужное место | `@iskatel` |
| Узнать, как это делается правильно (интернет, документация) | `@dokop` |
| Составить план и список проверок **до** начала | `@proektirovschik` |
| Написать код по готовому плану | `@programmist` |
| Запустить тесты и проверки, доказать, что работает | `@proveryalschik` |
| Посмотреть на результат честно, ничего не правя | `@retsenzent` |
| Секреты, пароли, доступы, безопасность | `@ohrannik` |
| Интерфейс и внешний вид | `@dizayner` |
| Таблицы, миграции, медленные запросы | `@bazy` |
| Сборка, деплой, серверы | `@devops` |
| Команды голосом | `@golosovoy` |
| Действия на компьютере: файлы, программы, скриншот | `@provodnik-pk` |

Правила выбора:

- **Агент — не замена собственной проверке.** Позвали `@proveryalschik` —
  значит дождаться его ответа и прочитать вывод, а не считать задачу
  закрытой по факту вызова.
- **Один агент — одна роль.** Не звать `@programmist` на ревью: для этого
  есть `@retsenzent`, и он по замыслу не имеет права вносить правки.
- **Сомнение — позвать.** Если непонятно, чья это роль, лучше спросить
  агента, чем угадывать.

## 4. Большая задача: работа в связке

Если задача крупная (несколько файлов, больше получаса, есть риск
сломать), порядок фиксированный:

1. `@proektirovschik` — план работы и список проверок.
2. **Показать план человеку и дождаться ответа.** Согласие молча
   согласием не считается.
3. `@programmist` — код строго по плану.
4. `@proveryalschik` — тесты и проверки по списку из шага 1.
5. `@retsenzent` — честный взгляд на результат.
6. `verification-before-completion` — и только после этого «сделано».
7. `visual-report` — показать, что получилось.

**Начинать скилл с середины цепочки нельзя.** Код без плана и без
проверок — это не «быстрее», это переделка.

## 5. Если результат не устроил

Самый важный раздел. Плохой результат — это не «плохо», это **информация**.
Дальше по шагам:

**Шаг 1. Сказать прямо, что именно не так.** Не «стараюсь исправить»,
а конкретно: что ожидалось, что получилось, где разница. Размытое
«не то» невозможно исправить.

**Шаг 2. Понять, чья это ошибка.**

- Понятие задачи было неверным → `brainstorming`, вернуться к обсуждению.
- План оказался негодным → `writing-plans`, переписать план.
- Код не соответствует плану → `test-driven-development`.
- Что-то сломалось и непонятно где → **`systematic-debugging`**.
  Никогда не чинить наугад: сначала найти причину, потом править.

**Шаг 3. Не выбрасывать сделанное.** Если часть работы годится —
починить точечно. Полное переписывание — крайность, и оно допустимо
только когда человек об этом попросил или старая основа неправильная
настолько, что чинить нечего.

**Шаг 4. Позвать `@retsenzent`.** Он смотрит на результат со стороны и
не вносит правок — именно поэтому видит то, что не видит автор. Это
дешёвый способ найти проблему до того, как её увидит человек.

**Шаг 5. Не повторять одну и ту же ошибку.** Если выяснилось, что решение
было неудачным, записать это в `facts.md` или `журнал-решений/<месяц>.md`
с датой. Иначе та же ошибка вернётся через месяц.

**Шаг 6. Проверить честно.** `verification-before-completion` — и только
после него «сделано». Непроверенное «готово» хуже, чем честное
«починил вот это, вот это проверить не смог».

### Чего точно не делать

- Молчать о проблеме и ждать, пока человек заметит сам.
- Говорить «готово» без запуска — проверка обязательна (это правило
  базы, а не пожелание).
- Правки в несколько заходов без проверки между ними.
- Менять работающее, чтобы «сделать красивее», без просьбы.

## 6. Где что лежит

| Что | Где |
|---|---|
| Этот файл | `инструкции/Скиллы-и-агенты.md` |
| Подробный список скиллов | `skills-index.json` |
| Папки скиллов | `skills/<имя>/SKILL.md` |
| Файлы агентов | `tools/agents/<имя>.md` |
| Кто над чем работал | `projects/<Проект>/<Нейросеть>/work.md` |
| Правила пользователя | `facts.md`, `настройки/запреты.md` |

Правило в этой базе одно и оно главное: **сначала проверка, потом
утверждение**. Всё остальное — способы не нарушить его.
