доказывает отсутствия вообще, и мост не имеет права говорить «не
установлено», если не проверил все источники своего списка.

Состояния, которые различаются при диагностике и не смешиваются:

1. приложение не найдено;
2. приложение найдено, CLI не найдена;
3. CLI найдена, но её работоспособность не проверена;
4. CLI запускается, авторизации нет;
5. CLI запускается, авторизация подтверждена.

Это **диагностические** состояния, а не гарантии доступности всех функций
программы. «CLI запускается» означает, что на неё ответил `--version`, а не
то, что она готова к любому вызову: совместимость версии, наличие входа и
полнота набора инструментов проверяются отдельно и могут оказаться другими.
Мост не имеет права выводить из состояния 5 «всё работает», а человек —
ждать от состояния 3 полноценной работы.

Вывод, ради которого всё и затевалось: **мост Codex не видит уже
установленную программу** только потому, что её нет в PATH.

## 2. Часть 1: автопоиск программы

### 2.1 Помощник

В `tools/dbapp/launchers/bridge_common.py`:

```
ProgramSpec(name, exe_names, extra_globs, config_hint, app_paths)
find_cli(spec, allow_batch=False) -> ProgramFound
```

`ProgramFound` — простой класс с полями:

| поле | смысл |
|---|---|
| `path` | найденный путь или пустая строка |
| `from_source` | `PATH`, `настройка программы`, `папка приложения`, `папка пользователя`, `ярлык «Пуск»`, `не найдено` |
| `checked` | проверяли ли мы найденный файл на работоспособность |
| `reason` | короткая причина, объясняющая **итог**: не нашли ни одного кандидата, все отклонены, все непроверяемы |
| `attempts` | список всех рассмотренных кандидатов: источник, путь, вид записи и результат |

Видов записи в `attempts` ровно три, и их нельзя сливать:

| вид записи | когда появляется | что означает |
|---|---|---|
| «кандидат обнаружен» | файл найден в своём источнике | найдено, но ещё ничего не запускалось |
| «отклонён политикой типа файла» | тип не допускается в текущем режиме | отказ в допуске, а не поломка программы |
| «проверка запуска выполнена» | запускался `--version` | вот теперь известно, работает файл или нет |

`reason` — это итог для человека, коротко. `attempts` — подробности: если
подряд не запустились три файла из двух папок, причина не теряется и не
перетирается, а человек в интерфейсе видит одну строку, а в диагностике —
полный перечень с ограничением по длине. Без разделения либо потеряется
первая причина, либо человеку высыплется список из двадцати ошибок.

`reason` обязателен, когда `path` пуст: «не нашли» — тоже результат, и он
попадает в сообщение, а не остаётся пустотой. Смысл разделения простой:
**файла нет** и **файл есть, но не работает** — это разные поломки, и
человеку нужны разные слова.

Тонкая обёртка `find_cli_path(spec) -> str | None` возвращает только `path`.
Новые вызовы идут через `find_cli`, потому что им нужен `reason`.

**Про пустое и «не найдено».** Внутри `ProgramFound.path` при неудаче
остаётся пустая строка — так записано в таблице полей. Обёртка наружу отдаёт
`None`: путь есть — строка, пути нет — `None`. Тип совпадает с прежним
`resolve_exe`, который тоже отдаёт `str | None`, иначе в местах вызова
пришлось бы различать два вида «нет программы» и забыть про один из них.
На «нет программы» обёртка не бросает исключение и ничего не подставляет.

Проверяется тестом, и различие проверяется явно: `find_cli_path` возвращает
`None`, `find_cli` — `ProgramFound` с пустым `path` и непустым `reason`.
Иначе различие между пустой строкой и `None` остаётся фразой в документе.

**Имя выбрано не случайно.** В пакете уже есть
`mcp_registry.find_program(name) -> str` (строка 519) — поиск программы по
имени и шаблону пути, совсем другое назначение; его зовут `blender_addon`
и разделы самопроверки. Второе `find_program` с другим смыслом и другим
типом возврата в одном пакете — ловушка и для читателя, и для
автодополнения, поэтому новое имя отличается.

**Что на самом деле обязан сохраниться — проверено по коду 15.10.2026.**
`find_cli_path` — **новая** функция, никаких прежних вызовов у неё нет,
и «совместимость с уже написанными вызовами» к ней не относится.
Прежний контракт, который обязан продолжить работать как был, —
`bridge_common.resolve_exe(name) -> str | None` (строка 47): его зовут
лаунчеры Codex и Cursor, мосты Spotify, TikTok, Unity и Unreal, а также
`engine_setup` пятью вызовами; `test_engine_setup.py` его подменяет.
Он возвращает **только первое** совпадение — и именно поэтому новый поиск
не может быть его обёрткой.

`app_paths` — пути, по которым видно, что приложение установлено, даже если
CLI нет. Нужны, чтобы отличить «Cursor не стоит» от «Cursor стоит, нужна CLI».

### 2.2 Порядок поиска — детерминированный

Источники идут строго по очереди, и в каждом кандидаты проверяются, пока не
найдётся пригодный:

1. **PATH.** Здесь важная поправка, сделанная по коду, а не по смыслу.
   Нынешний `resolve_exe` возвращает **только первое** совпадение: он зовёт
   `shutil.which` и, если тот что-то нашёл, сразу выходит. Значит обещанного
   перебора кандидатов в PATH сегодня нет: если первая копия `claude.cmd` в
   PATH не запускается, вторая, ниже по списку папок, никогда не будет
   рассмотрена — мост просто пойдёт к следующему источнику.
   Поэтому новый перебор сам обходит все папки PATH и собирает **все**
   совпадения для имени и для `.cmd`, `.exe`, `.bat`, и проверяет их по
   очереди. Собираются все типы: это **сбор совпадений, а не разрешение их
   запуска**, отбор по типу файла делает следующий этап. Старый `resolve_exe`
   для этого не годится и остаётся как был.
2. **Путь из настроек самой программы.** Для Codex — строка
   `CODEX_CLI_PATH` в `~/.codex/config.toml`.
3. **Папка приложения.** Маски вида
   `%LOCALAPPDATA%\OpenAI\Codex\bin\*\codex.exe`.
4. **Папка пользователя.** `~\.local\bin`, затем `%APPDATA%\npm`.
5. **Ярлык в меню «Пуск».** Читается цель ярлыка, ничего не запускается.

**Самый свежий файл — ещё не значит рабочий.** Обоснование не умозрительное:
15.10.2026 чинился uv, где в обеих папках `python.exe` имел размер 0 байт,
и «самый свежий» файл был бы битым.

Кандидат проходит четыре ступени, и они группируются в **два разных этапа**:
сначала порядок обхода, потом допуск. Смешивать их нельзя — иначе «кто
первый» и «кого можно запускать» решаются одним правилом, и это правило
быстро становится неверным.

**Этап порядка — ступени 1 и 2: кого смотрим первым.**

1. отсев по существованию: файл отсутствует или размер 0 байт — причина в
   `reason`;
2. упорядочивание — **правило своё для каждого источника**, потому что у них
   разная природа:

   | источник | порядок кандидатов внутри источника | почему так |
   |---|---|---|
   | **PATH** | порядок папок PATH как в переменной окружения; **время изменения не учитывается**; при нескольких совпадениях в одной папке — по имени файла | PATH сам по себе список приоритетов, заданный системой. Сортировать его по дате — значит переписать чужое решение о порядке своим |
   | **папка приложения** (маски с `*`) | самый свежий по времени изменения; при равных датах — лексикографически больший путь | в папке лежат сборки разных версий, и свежая обычно нужная; обоснование — починка uv, где в обеих папках был битый файл нулевого размера |
   | **настройки программы** | единственный путь из настроек, порядок не нужен | путь один, сравнивать нечего |
   | **папка пользователя** (`~\.local\bin`, `%APPDATA%\npm`) | по порядку перечисления папок; внутри папки — по имени файла, без учёта даты | это продолжение PATH-поведения, а не папка версий |
   | **ярлык «Пуск»** | по порядку перечисления ярлыков, ничего не запускается | цель читается, порядок определяется только перечислением |

   Сортировка по дате к PATH **не применяется**, и это не упущение, а
   следствие того, что порядок PATH уже задан кем-то другим. Критерий 3
   говорит о выборе в папке приложения, критерий 33 — о порядке PATH, и
   противоречия между ними нет ровно потому, что это два разных правила.

**Этап допуска — ступени 3 и 4: можно ли его вообще запускать.**

3. политика по типу файла: `.exe` — запуск с `--version`, таймаут 15 секунд;
   `.cmd` и `.bat` — только при `allow_batch=True`, иначе отказ до
   `probe_candidate` и до любого запуска (раздел про пакетные файлы); прочие
   расширения — только наличие и размер, запускать нечем;
4. результат проверки: код 0 — кандидат пригоден; ненулевой код, таймаут или
   не запустился — причина в `reason`, берём следующего кандидата.

**Тип файла в сортировку не входит, и это решение, а не упущение.** Никакого
«`.exe` всегда лучше» здесь нет: более свежий кандидат другого типа не
становится хуже оттого, что он не `.exe`, а более старый `.exe` не побеждает
только по своему расширению. Обоснование не в том, что тип не важен, — он
важен, и на следующем этапе решает всё, — а в том, что подставлять его в
порядок обхода значило бы объявить свежесть второстепенной перед удобством
запуска. Это отдельное продуктовое решение, которого контракт не требует.

**Обнаружение не равно разрешению на запуск.** Поиск находит совпадения, и
найденное само по себе не даёт права что-то запускать:

- при `allow_batch=False` кандидаты `.cmd` и `.bat` отклоняются до
  `probe_candidate` и до любого запуска — **в том числе совпадения, найденные
  в PATH**;
- при `allow_batch=True` пакетные файлы допускаются к общей политике
  проверки, и сам факт допуска не означает, что они безопасны или подходят
  любому мосту;
- мост агента получает найденный и проверенный `.exe` и передаёт его в
  `prepare_argv` **абсолютным путём**; возвращаться к разрешению по одному
  имени нельзя.

**Отказ в допуске не должен выглядеть как поломка программы.** В `attempts`
различаются три вида записи: «кандидат обнаружен», «отклонён политикой типа
файла» и «проверка запуска выполнена». `reason` описывает **итог поиска**,
поэтому отклонённый `.cmd`, после которого нашёлся рабочий `.exe`, в
`reason` не попадает: итог там один — работающая программа найдена. Иначе
человек прочитает «отказ по типу файла» как «программа сломана» и пойдёт
чинить не то.

Кандидаты источника кончились все — переходим к следующему источнику, а не
сдаёмся. Порядок при любом раскладе машины один и тот же: если CLI есть и в
PATH, и в папке приложения, проверяется PATH; если файл из PATH не
запускается, идём дальше по списку, а не останавливаемся на первом же.

**Что такое проверка `--version`.** Это проверка запускаемости: отвечает ли
файл и не зависает ли он. Это **не** проверка безопасности и не проверка
совместимости версии — доверяем мы этому файлу ровно настолько, насколько
доверяем самой программе, чей путь нашли.

Проверка запускается только для кандидатов из своего списка. Путь, пришедший
из команды агента, проверкой не проходит никогда.

### 2.3 Что говорит мост

- нашли в PATH — «команда codex найдена в PATH»;
- нашли не в PATH — «codex найден не в PATH, а в папке приложения: …»;
- CLI нет, приложение есть — «Cursor установлен, но мосту нужна Cursor CLI.
  Поставь: <официальная команда>»;
- нет ни того, ни другого — старая честная строка про winget.

Команды установки берутся из документации, и рядом в коде пишется, откуда:
Cursor — `cursor.com/docs/cli/installation`, Claude — `docs.claude.com`
(раздел setup).

### 2.4 Правила безопасности

- Обход списка только читает: папки, ярлыки, `~/.codex/config.toml`. Реестр
  читается, но не пишется.
- **Запуск — отдельное действие.** Проверка `--version` и команда проверки
  входа запускают чужой код, поэтому формулировка «поиск ничего не запускает»
  была бы неверной. Правильно: запуск делается только для кандидата из
  своего списка, только с коротким таймаутом и только с `--version` либо с
  командой проверки входа. Никаких других команд мост не запускает.
- Аргумент из команды агента никогда не становится путём к программе:
  перебор только по своему списку, проверяется только свой список.
- Ничего не ставится, не обновляется и не удаляется.

## 3. Часть 2: мост Claude

### 3.1 Основание

`docs.claude.com/en/docs/claude-code/cli-reference` и `/headless`,
прочитаны 15.10.2026:

| что | как в документации |
|---|---|
| неинтерактивный запрос | `claude -p "query"` |
| текст ответа в JSON | `--output-format json`, поле **`result`** |
| идентификатор сессии в JSON | **`session_id`**, верхний уровень |
| продолжить разговор | `--resume <id>`; вместо id можно дать путь к `.jsonl` |
| проверка входа | `claude auth status` — код **0**, если вход есть, **1**, если нет; поле `authMethod` |
| вход | `claude auth login` (браузер) |
| коды завершения | «exits with code 0 on success and a non-zero code when the run fails» — код **0** при успехе, ненулевой при сбое запуска |
| ошибка внутри запуска | **пересказ, дословность не сверялась:** по документации при некоторых ошибках выполнения текст ошибки может попадать в поле результата |
| опасное | `bypassPermissions`, `--dangerously-skip-permissions` — **не передаём никогда** |

**Про строку про ошибку внутри запуска — почему это пересказ, а не цитата.**
Формулировка была записана кавычками, но точный первоисточник не
подтверждён, а кавычки читаются как «э verbatim сказано в документации».
Подтверждено документацией на 15.10.2026 другое: формат JSON с полем
`result`, режим `-p`, приём `--disallowedTools` отдельными именами и
требование v2.1.259+ для `--permission-prompts none`. Эти четыре пункта
опираются на сверенный источник, строка про ошибку внутри запуска — нет.

Сам контракт разбора от этого не зависит: код завершения, `stdout`, `stderr`
и поле `result` разбираются раздельно в любом случае, потому что сверена
структура ответа, а не наличие конкретной фразы в документации.

Документированный пример из раздела Continue conversations, из которого
взято поле id:

```bash
session_id=$(claude -p "Start a review" --output-format json | jq -r '.session_id')
claude -p "Continue that review" --resume "$session_id"
```

### 3.2 Почему одного `plan` мало — и что вместо него

Из документации о режимах: `plan` — «Claude reads files and runs read-only
shell commands to explore but doesn't edit your source files; **with auto mode
available, classifier-approved commands also run**».

То есть `plan` запрещает правку исходных файлов, но не является жёсткой
границей: часть команд может пройти через классификатор. Для моста, у
которого никто не сидит и отвечать не на что, берём связку:

| флаг | что даёт по документации |
|---|---|
| `--permission-mode plan` | не правит исходные файлы |
| `--permission-prompts none` | «Anything that would prompt is denied», хост не опрашивается и не ждётся его; требует v2.1.259+ |
| `--disallowedTools` и четыре отдельных аргумента: `Edit`, `Write`, `NotebookEdit`, `MultiEdit` | правило deny убирает инструмент из контекста модели целиком. Форма **только такая**: пять отдельных элементов argv. Перечисление через запятую в этой таблице не приводится намеренно, чтобы его нельзя было скопировать в реализацию буквально (см. 3.3) |

**Ограничения безопасности — честная формулировка.** Мост передаёт Claude Code
режим `plan`, отключает ожидание разрешений и запрещает инструменты
редактирования. Это ограничивает набор действий, доступных модели, но **не
гарантирует невозможность изменения файлов**. Запрет инструментов не
распространяется на:

- команды оболочки с перенаправлением (`> файл`, `>> файл`, `tee`);
- команды вроде `find -delete`, `sed -i`, `cp`, `mv`, `mkdir`;
- «arbitrary subprocesses that read or write files indirectly» — прямая
  цитата документации: правила Claude Code такие вызовы не проверяют;
- всё, что появится в будущих версиях Claude Code.

Полной границы здесь нет: её дала бы изоляция на уровне ОС, а её мы не
используем и не собираемся. Отсюда два правила:

1. Мост **не заявляет** в ответе, что рабочая папка защищена от изменений.
2. **Предупреждение — постоянное свойство моста, а не реакция на текст
   запроса.** Оно есть в описании инструмента и в диагностике и показывается
   всегда, а не только когда запрос «явно предполагает изменение файлов».
   Причина практическая: определить намерение по тексту надёжно нельзя —
   человек просит «проверь проект», а модель сама решает запустить команду с
   побочным эффектом. **Распознавание намерения не является защитной
   границей** и опираться на него нельзя.
3. Для конкретного запроса, который прямо говорит о правке файлов, мост
   добавляет более заметное предупреждение — но это дополнение, а не
   основание: отсутствие такого текста запроса защиту не отменяет.

Предупреждение само по себе не защищает — оно нужно, чтобы не создавать
ложного ощущения защищённости.

**`--bare` не передаём.** Документация называет его рекомендуемым для
скриптов, но в том же абзаце: в bare-режиме Claude Code «never reads OAuth
credentials or the system keychain» и работает только по `ANTHROPIC_API_KEY`.
Без него мы потеряли бы вход по подписке — ровно то, ради чего мост и
существует.

### 3.3 Инструменты и обязательные флаги

Оба вызова **заново собирают полный набор обязательных ограничений**.
`claude_send` отличается от `claude_new_chat` только добавлением
`--resume <id>`: ограничения не ослабляются и не заменяются. Сохранённое
состояние прошлой сессии не считается заменой проверки аргументов нового
процесса — флаги задаются на каждый запуск и решают всё первыми.

| инструмент | команда |
|---|---|
| `claude_new_chat` | `claude -p <текст> --output-format json --permission-mode plan --permission-prompts none --disallowedTools Edit Write NotebookEdit MultiEdit` |
| `claude_send` | та же строка плюс `--resume <id>` |

**Про `--disallowedTools` — формат отдельными аргументами, не через запятую.**
Это исправление найденной при ревью ошибки. Документация показывает ровно два
вида значения этого флага: несколько отдельных аргументов с конкретными
именами (`"Edit" "Write" "NotebookEdit"`) и один аргумент с маской
(`"mcp__*"`). Форма «четыре имени через запятую в одной строке» не встречается
ни разу. Если CLI посчитает такую строку одним именем инструмента, запрет
не сработает, а мост будет утверждать, что запретов три.

Поэтому: `--disallowedTools` и следующие четыре имени — **пять отдельных
элементов argv**. Тест обязан проверять не наличие флага, а что запрещены
все четыре по отдельности, иначе опечатка в формате снова пройдёт незамеченной.

**Проверка версии до первой команды.** Обязательный набор менялся между
версиями: `--permission-prompts none` требует v2.1.259+. Мост не имеет
права молча выбросить неподдерживаемый флаг и продолжить — ограничения
оказались бы слабее заявленных. Поэтому перед первым вызовом:

1. версия читается командой `claude --version` (тот же `probe_command`,
   таймаут 15 секунд);
2. версия разбирается, недостающая — отказ с понятным текстом: «Claude Code
   версии X, а нужно Y: без этого мост не может включить ограничения, о
   которых говорит»;
3. версия не прочиталась — **мост не запускает вызов**, а говорит: «версию
   проверить не удалось, ограничения не проверены»;
4. проверка идёт один раз при старте лаунчера, результат попадает в журнал
   и в окно.

Ещё одна деталь про `--permission-prompts none`: для версий старше минимума
CLI отвечает ошибкой о неизвестном аргументе. Наш контракт разбора (3.4)
должен отличать такую ошибку от ошибки входа, иначе человек будет читать
«войди» вместо «обнови Claude Code».

**stdin у ребёнка закрыт.** Документация прямо говорит: «Non-interactive
mode reads stdin», а конвейер ограничен 10 МБ. Если отдать ребёнку канал
протокола MCP, он будет читать наши сообщения — ровно тот дефект, который
найден у `codex exec` в живё 15.10.2026 (420 секунд тишины и потерянные
сообщения). Поэтому `stdin=DEVNULL` здесь не украшение, а обязательное
требование.

Проверяется это не «процесс не завис», а прямо: заглушка, которая читает
stdin, должна получить пустой поток и завершиться, а сообщение протокола
остаться нетронутым и разобранным.

**Заглушка пишет о своём потомке достаточно, чтобы его потом можно было
опознать.** Одного номера процесса мало: номер переиспользуется, и проверка
«жив ли такой PID» может увидеть чужую программу. Поэтому в файл
заглушка кладёт **номер, имя образа и время создания**, и проверка идёт по
всем трём. Если заглушка не может сообщить время создания, она обязана
сообщить об этом явно, и тест на такой случай падает с пометкой — молча
считать его пройденным нельзя.

**Про `.cmd` и `.bat` — отдельные правила, потому что через них идёт `cmd`.**
Сборка argv списком защищает от разбора командной строки в Python, но
`.cmd` и `.bat` Windows запускает только через `cmd.exe`: общий
`prepare_argv` подставляет `cmd /c` и передаёт аргументы следом. Дальше
`cmd` разбирает **всю** командную строку заново — и в неё попадают не
только путь, но и текст запроса.

Полный список метасимволов `cmd`, а не четыре символа:

| символ | что делает |
|---|---|
| `%` | разворачивается как переменная окружения |
| `!` | опасен при включённом отложенном расширении |
| `^` | экранирование следующего символа |
| `"` | ломает кавычки и всю конструкцию |
| `&` | разделитель команд — можно дописать запуск второй команды |
| `\|` | конвейер |
| `<` `>` | перенаправление, в том числе запись в файл |
| `(` `)` | группировка команд |
| перевод строки | новая команда |

Четыре символа из прошлой редакции были неполными: `&`, `|`, `<`, `>`,
скобки и перевод строки опасны не меньше.

**Решение: мосты к агентам не используют `.cmd` и `.bat` вообще.**
Проверять правила экранирования `cmd.exe` — отдельная исследовательская
работа: у `cmd` нет кавычек, которые одинаково работают во всех случаях, и
доказать безопасность для произвольного текста модели здесь дороже, чем
отказаться.

**Кто именно отказывает и на каком шаге.** Интерфейс закреплён явно, иначе
правило разъедуется:

- общий поиск умеет находить кандидатов и собирает историю попыток;
- отказ от пакетного файла делают **мосты к агентам**: они зовут поиск с
  `allow_batch=False`;
- отказ происходит **до** проверки запуска и тем более до запуска чего бы то
  ни было;
- остальные мосты сохраняют прежнее поведение.

```
find_cli(spec, allow_batch=False) -> ProgramFound
```

| тип кандидата | проверка |
|---|---|
| `.exe` | размер больше нуля, затем `--version`, таймаут 15 секунд |
| `.cmd`, `.bat` | только при `allow_batch=True`; иначе отказ до запуска |
| прочее | наличие и размер; запускать нечем, поэтому и проверять нечем |

Человек получает текст: «найдена npm-версия, она запускается через
cmd.exe, а мост через неё не работает. Поставь нативную версию» — с
названием того, что нужно поставить.

**Границы применимости.** Собственные фиксированные команды программы не
затрагиваются: `npx -y <пакет>` в мосте Spotify зовёт `prepare_argv` напрямую
и в новый поиск не ходит. Правило не распространяется на `bridge_common`
целиком — иначе мы бы сломали работающий мост Spotify.

**Дыра, найденная при сверке с кодом: `prepare_argv` возвращает `.cmd`
сам.** Он начинается с `resolve_exe(argv[0])` (строка 76). Если лаунчер
передаст в `argv[0]` **имя**, а не найденный путь, `resolve_exe` снова
пройдёт PATH — и первым там может оказаться `claude.cmd`, который мост
только что отверг. Отказ оказался бы декларацией, а запуск обошёл бы её с
другой стороны.

Поэтому в лаунчер передаётся **абсолютный путь к найденному `.exe`**. Тогда
в `resolve_exe` срабатывает первая ветка, `Path(name).is_file()`, путь
возвращается как есть, и `.cmd` подмениться уже не может. Отказ
обеспечивается устройством, а не намерением. Проверяется отдельным
тестом, который кладёт рядом с `.exe` `.cmd`-обманку и требует, чтобы
запустилась `.exe`, а файл-признак у `.cmd` не появился.

Отдельной проверки «безопасна ли строка для cmd» не будет: при отказе от
пакетных файлов она оказалась бы защитой, которой никто не пользуется.
Для `.exe` текст запроса передаётся отдельным аргументом через `subprocess`
**без запуска `cmd.exe`**, поэтому метасимволы `cmd.exe` не интерпретируются
как команды оболочки. Формулировка «разбора командной строки не происходит»
была слишком категоричной: Windows собирает командную строку из списка
аргументов, и корректность такой передачи проверяется тестами, а не
объявлением.

У обоих инструментов есть необязательный `workspace` — папка, в которой
работает Claude. Правила и граничные случаи — раздел 4.

Ограничения текста запроса — как у `codex_new_chat`: до 8000 символов, не
начинается с дефиса, один аргумент (пробелы не рвутся), id без пробелов и
без ведущего дефиса.

### 3.4 Контракт разбора ответа

Разбираются шесть независимых вещей: код завершения процесса, `stdout`,
`stderr`, корректность JSON, наличие и содержание `result`, наличие
`session_id`. Свести их к одному признаку «успех или ошибка» нельзя.

| ситуация | что делаем |
|---|---|
| код 0, JSON корректен, `result` непустой | отдаём `result` и `session_id`, если он есть |
| код 0, JSON корректен, `result` пуст | «Claude не вернул текст», без домыслов |
| код 0, JSON нечитаем | «ответ не разобрался»; текст из stdout пользователю **не** выдаётся за ответ модели |
| код не 0, stdout — корректный JSON | код попадает в ответ, JSON разбирается; успехом это **не** считается |
| код не 0, JSON отсутствует или нечитаем | «Claude ответил кодом N», затем `stderr`, затем доступный `stdout` — каждый кусок с пометкой, откуда он |
| процесс не запустился (OSError) | «Claude не запустился: <причина>», отдельно от ошибок Claude |
| процесс не ответил за таймаут | «Claude не ответил за N секунд»; процесс завершается по правилам 3.6 |

**Порядок текста в ответе.** Сначала строка моста о том, что произошло,
затем диагностика из `stderr`, затем текст из `stdout`. Диагностика из
`stderr` **никогда** не выдаётся за ответ модели и не подставляется в поле
`result`: по документации при некоторых ошибках выполнения текст ошибки может
попадать в поле результата (пересказ, дословность не сверялась — см. 3.1), и
без разделения пользователь решит, что это слова Claude. Правило действует
независимо от формулировки документации: смешивать диагностику и ответ нельзя
в любом случае.

**`session_id` — одно поведение, а не два.** Чтобы два исполнителя не
реализовали разные контракты, зафиксировано так:

- извлекается **только** из корректного JSON, никогда не выдумывается;
- при ошибке идентификатор **сохраняется во внутреннем результате** для
  диагностики, но статус остаётся ошибочным;
- мост **не объявляет** разговор успешно созданным и **не предлагает**
  продолжить его как рабочую сессию — сначала человек читает причину сбоя;
- в тексте ответа идентификатор при ошибке показывается только как
  диагностическая пометка, а не как «вот твой чат»;
- при отсутствии — «id сессии не вернулся, продолжить этот разговор нечем».

**Таймаут и дерево процессов.** Время ожидания берётся тем же, что у
остальных мостов этой семейства (600 секунд на вызов), отдельного числа не
выдумываем.

Истёк таймаут — значит останавливается **всё дерево**, а не только прямой
процесс. Это важно и зафиксировано по коду: `subprocess.run(timeout=…)`
убивает только того, кого запустил, а потомки остаются жить. В проекте
приём уже есть и используется в `lmarena.py` и `pxpipe.py` —
`taskkill /PID <pid> /T /F` плюс `CREATE_NEW_PROCESS_GROUP`; мосты его не
используют. Правило для всех затронутых мостов, не только нового: по
таймауту завершается дерево, ресурсы освобождаются, в ответе прямо сказано,
что остановка принудительная.

Это не теория. 15.10.2026 при прогонах самопроверки и зондов дважды
пришлось вычищать осиротевшие процессы — 8 и 22 штуки. У комплектного
Codex, кстати, есть чем плодиться: в его папке лежат `codex-command-runner.exe`
и `codex-windows-sandbox-setup.exe`.

### 3.5 Проверка входа

`claude auth status`: код 0 — «вход есть», 1 — «входа нет, войди сам:
claude auth login». Команда не ответила — «вход не проверялся». Слова берутся
из документации, а не придумываются.

**Единственная команда авторизации, которую запускает мост, —
`claude auth status`.** Мост никогда не выполняет `claude auth login`, не
`codex login` и не `agent login`. Браузер не открывается, и это запрет на
запуск команд входа, а не обещание, что откроется только он.
Вход делает человек, и мост только говорит, что это нужно.

**Про `~/.claude` обещаем меньше, чем хочется.** Запрет касается действий
**авторизации**: мост не запускает команду входа и не изменяет файлы
авторизации собственным кодом. Чего мост **не** обещает — отсутствия всех
побочных записей: при обычном запуске сам Claude Code может сохранять данные
сессии и другие служебные файлы. Обещать «каталог не меняется» было бы
неправдой, которую нечем проверить, и она противоречила бы 3.2, где уже
сказано, что ограничения моста не заменяют изоляцию на уровне ОС.

Проверяется не имя команды, а **весь передаваемый argv целиком**:

```
["<абсолютный путь к claude.exe>", "auth", "status"]
```

Три элемента: исполняемый файл и два аргумента после него — `auth` и
`status`. Прежняя формулировка «ровно два аргумента» без указания позиции
была двусмысленной: в Python `argv` включает сам исполняемый файл, и «ровно
два» можно было прочитать как «два всего». Если в списке окажется что-то
ещё (например, путь к конфигурации или флаг входа), это отказ с причиной, а
не запуск. Тест сверяет список целиком, а не отдельные слова: наличие
правильных слов при лишнем четвёртом элементе — это уже другая команда.
Такой критерий ловит попытку «заодно проверить вход», которая выглядит
безобидно, но открывает браузер.

Классификация не сводит лишние состояния к одному, иначе человек получит
«войди» там, где CLI просто сломана:

| состояние | что показываем |
|---|---|
| CLI не найдена | приложение стоит или нет + команда установки |
| CLI найдена, но не запускается | «найдена, но не запускается: <причина>» — про вход здесь не говорим |
| проверка входа сама упала | «вход проверить не удалось: <причина>» — не «входа нет» |
| входа нет | «входа нет, войди сам: claude auth login» |
| вход подтверждён | «вход есть» + значение `authMethod`, если вернулось |

**Ненулевой код — ещё не «входа нет».** Код **1** по контракту означает
отсутствие входа. Любой **другой** ненулевой код, а равно нечитаемый или
пустой вывод — это «проверка упала», иначе человек получит «войди» там, где
CLI просто сломана.

Это различие опирается на документацию, и **до появления установленной CLI
его нужно подтвердить живым прогоном**. Подтверждения нет — состояние «входа
нет» остаётся недоказанным, и мост говорит «вход проверить не удалось» вместо
того, чтобы утверждать отсутствие входа на основании непрочитанного кода.

### 3.6 Единый результат вызова

Один внутренний формат на всё, чтобы отдельно формировать ответ MCP, строку
журнала и строку таблицы, не смешивая их:

| поле | смысл |
|---|---|
| `status` | `ок`, `ошибка_процесса`, `ошибка_разбора`, `ошибка_входа`, `таймаут`, `ошибка_остановки`, `не_совместимо` |
| `exit_code` | код завершения, если процесс запускался |
| `text` | то, что видит человек: короткая первая строка |
| `detail` | диагностика: `stderr` и доступный `stdout`, с пометкой источника |
| `session_id` | извлечённый из корректного JSON, иначе пусто |
| `reason` | для интерфейса: чего не хватает и что делать |

Правила наполнения:

- `text` — всегда своя фраза моста, никогда не сырой вывод программы;
- `detail` — обрезается до 2000 символов, как у Codex и Cursor;
- `session_id` при статусе ошибки не поднимает статус до `ок` (правило выше);
- при таймауте `detail` объясняет, что процесс остановлен по таймауту
  моста, и это не выглядит как «Claude не ответил, потому что сломался».

**Три результата по времени не сливаются в один `таймаут`.** Различие нужно
вызывающему коду и интерфейсу, а не только читателю журнала: «процессы
остановлены» и «могли остаться работать» — это разные ситуации, и вторую
человеку надо увидеть.

| результат | когда | что видит человек |
|---|---|---|
| `таймаут` | время вышло, дерево процессов подтверждённо остановлено | «не ответил за N секунд, процесс остановлен» |
| `ошибка_остановки` | время вышло, но подтверждения, что дерево исчезло, нет | то же и «остановить не удалось», с номерами оставшихся процессов |
| `ошибка_процесса` | запуск или выполнение завершились с ошибкой без таймаута | обычный текст ошибки |

**Код 0 у `taskkill` — ещё не доказательство, что всё исчезло.** Команда
может отработать успешно, оставив процесс, и может не найти его и тоже вернуть
0. Поэтому очистка считается выполненной **только после проверки самих
процессов**: после `taskkill` мост убеждается, что записанные номера
действительно не живут — иначе результат `ошибка_остановки` с номерами
оставшихся, чтобы человек разобрался.

Проверка идёт по номерам процессов, а не по журналу и не по коду команды:
проверяется, например, через `tasklist /FI "PID eq N"` или через
`OpenProcess` с нулевым дескриптором. Какой именно способ выбран — деталь
реализации, но требование одно: **очистка подтверждена или не подтверждена**,
а не «команда выполнена». Этот способ проверяется тестом: заглушка
удерживает потомка, который не умирает вместе с родителем, и тест обязан
получить `ошибка_остановки`, а не `таймаут`.

**Фильтр секретов должен быть отказоустойчивым.** Значение ключа, если оно
мелькнуло в тексте, заменяется на `[скрыто]`. Четыре обязательных случая:

| случай | поведение |
|---|---|
| очень длинное значение | сравнение и замена по всей длине, без обрезки значения до поиска |
| значение разбито на несколько строк | ищется и по частям, и по исходному виду; несобранное не проскакивает |
| значение попало в URL или закодировано | ищется также закодированная форма; если найдена — тоже заменяется |
| фильтр сам упал или получил не строку | **диагностика не выдаётся вовсе**: в ответе остаётся только своя фраза моста |

Последняя строка — самая важная. Худшее, что может случиться, — фильтр
сбоит и исходный `stderr` уходит в ответ MCP вместе с секретом. Поэтому
принцип такой: **лучше не показать диагностику, чем показать её
неотфильтрованной**. Отказ фильтра — это `detail = пусто` и понятная причина
в `reason`, а не «показать как есть».

**Порядок обязателен: фильтр идёт до журнала.** Сырой `stderr` не пишется в
журнал ни разу и ни на каком промежуточном шаге. Сначала фильтр строит
`detail`, и уже отфильтрованное попадает и в ответ инструмента, и в журнал.
Иначе фильтрация ответа не спасёт: секрет уже в логе.

При сбое фильтра в журнал не попадает **ни** исходный `stderr`, **ни** текст
исключения фильтра — туда тоже могут попасть секретные данные. Остаётся
только заранее определённая фраза моста.

Проверяется тестом, который подсовывает заведомо известное значение ключа в
**каждом** обещанном представлении — исходном, процентно закодированном, с
плюсом вместо пробела и с HTML-экранированием — и требует, чтобы ни одно из
них не встретилось ни в ответе, ни в файле журнала. Проверка только исходной
строки была бы слишком слабой: она доказала бы отсутствие одной формы и
пропустила бы утечку закодированной.

## 4. Граничные случаи аргумента workspace

| что пришло | что делаем |
|---|---|
| пустая строка | текущая папка лаунчера, `workspace` в ответе не печатаем |
| существующая папка | берём её |
| папки нет | отказ: «Папка workspace не существует. Чужой путь не подставляю» |
| это файл, а не папка | тот же отказ |
| **относительный путь** | **всегда отказ**: относительно чего разрешать — заранее неизвестно, cwd у сервера может быть любым |
| путь с `..` | разворачиваем в абсолютный и только потом проверяем существование; если не существует — отказ |
| пробелы и кириллица | разрешены и обязаны работать: argv собирается списком, кавычки Windows ставит сама. Отдельный тест на `C:\Мои документы\Проект (копия)` |
| спецсимволы `& | < > ^ % !` | разрешены: командная строка не собирается склейкой. Тест на имя с `&`. Действует потому, что мост запускает нативный `.exe`, передаёт путь отдельным аргументом и **не использует `cmd.exe`** |
| путь длиннее 260 знаков | отказ с отдельным текстом про длину пути, а не «не существует». Длина считается **по нормализованному** пути, не по строке аргумента: иначе отказ зависит от того, как именно папка названа |
| сетевой путь `\\server\share` | отказ: это уже не локальная папка |
| символическая ссылка или junction | допускаются, но нормализованный путь попадает в текст ответа, чтобы человек видел, куда на самом деле ведёт папка |
| папка исчезла между проверкой и запуском | отказ с текстом про исчезновение; **не** подставляем другую папку и не зависаем |

**Граница правила про спецсимволы.** Эти символы опасны не сами по себе,
а тем, что при запуске через `cmd.exe` становятся синтаксисом командной
строки — см. 3.3. В `workspace` путь идёт в argv списком и запускается `.exe`
без `cmd.exe`, поэтому символы разрешены и обязаны работать. Если бы запуск
шёл через пакетный файл, то же правило перестало бы действовать: именно
поэтому пакетные файлы для мостов к агентам не используются вовсе.

Порядок действий с аргументом, чтобы правило было одно: привести к
абсолютному (`Path.resolve()`), развернуть `..`, отклонить относительный
путь **до** нормализации, затем проверить существование и тип, затем длину,
и только после этого использовать.

Сам `resolve()` может не выполниться: нет прав на папку, обрыв или петля
символических ссылок, путь слишком длинный для системы. Все такие
исключения перехватываются и превращаются в тот же понятный отказ с текстом
причины. Необработанное исключение наружу не выходит: вместо сообщения
человек получил бы трассу, а это тот же класс отказов, что мы уже ловили
с окнами и с jsonc-конфигом.

Пустая строка — это не «случайный текущий каталог процесса», а папка,
заданная контрактом лаунчера при старте; она же подставляется по умолчанию
в `claude_send`.

## 5. Логирование и что видит человек

**Журнал (только stderr, протокол не трогаем).** Строки вида
`[codex-bridge] …`, `[claude-bridge] …`, `[cursor-bridge] …`:

- одна строка при старте: откуда нашли программу либо что её нет;
- одна строка о версии и одна о входе;
- **обычный успешный вызов не пишет ничего** — журнал не растёт от запросов
  агента;
- пишется только то, что требует диагностики: таймаут, неудачная остановка
  дерева процессов, отказ фильтра секретов, несовместимая версия.

**Что считается «требующим диагностики», решено явно,** иначе две
формулировки выше противоречили бы друг другу: строка пишется не на каждый
вызов, а только на перечисленные события. Обычный ответ модели в журнал
не попадает — ни текст, ни размер.

Политика вывода:

| что | можно ли в журнал |
|---|---|
| полный путь найденной CLI | **можно** — человек должен видеть, откуда запустилась программа |
| путь к папке настроек пользователя (`mcp-*.txt`, `config.toml`) | нельзя: имя файла можно, содержимое и полный путь нельзя |
| ключ, токен, значение `client id` | нельзя, никогда; на их место — «прочитан, в журнал не пишу» |
| диагностика из `stderr` | можно, но через фильтр секретов и с обрезкой до 2000 символов |
| содержимое вызова `workspace` | можно: это путь на диске, а не секрет |

Секрет считается секретом не по имени поля, а по факту значения: если
известное значение ключа мелькнуло в тексте, оно заменяется на `[скрыто]`.
Отдельная проверка идёт по всем сообщениям, а не только по журналу: текст
из `stderr` попадает в ответ инструмента, значит фильтр обязан работать и
там.

Если программа пишет очень много или не заканчивает — работает таймаут
(3.6), а вывод обрезается; в журнал уходит размер, а не содержимое целиком.
Такая строка пишется **только при таймауте**, а не при каждом вызове.

**Окно настройки.** Подсказка в одну-две строки: что нашли, что мешает,
одна команда установки, если мешает CLI. Без лишних слов и без кода ошибки.

**Таблица мостов.** Дырка — коротко и только про то, что мешает: «входа
нет — codex login». Нулевые коды, имена файлов и трейлеры в таблицу не
попадают.

**Ответ инструменту.** Первая строка ответа — про то, что произошло, и
только потом текст программы. Как сейчас у Codex и Cursor: подсказка о
входе идёт первой строкой, дальше код и текст.

## 6. Реестр и интерфейс

- Новая запись `claude`: категория «чаты», подключение `local`, команда через
  `quiet_launcher.py`, шаги настройки и «готовым не считаем» — по образцу
  Codex и Cursor.
- `engine_setup.py`: `claude_ready()` и `claude_gap()` по образцу
  `codex_ready()`/`cursor_ready()`, но с `claude auth status`.
- `tray_panel.py`: категория для нового сервера.
- `main.py`, HelpTab: раздел про Claude рядом с Codex и Cursor; там же честная
  строка, что ChatGPT — это ключ API, а мост codex — разговор по подписке.
- `selftest.py`: ожидаемое число — не «числа в трёх местах», а **две
  именованные константы**, по одной на конфигурацию. По коду на 15.10.2026
  литерал `22` стоит дважды: строка 10930 сверяет число серверов, строка
  11023 — число представлений. Оба заменяются ссылкой на константы; какая из
  конфигураций проверяется, задаётся параметром самопроверки, а не тем, что
  оказалось в реестре.

Числа в самопроверке — известная хрупкость: они повторяются в нескольких
местах, и добавление моста ломает их все сразу. Поэтому: ожидаемое число
задаётся один раз, а остальные места сверяются с фактическим реестром, а не
между собой; и отдельно оговаривается ожидаемое число для каждой из двух
конфигураций (23 без моста плеера, 24 с ним), чтобы «сломалось» не означало
«не сойдётся с соседней цифрой».

**Ожидаемое число обязано быть независимым от самого реестра.** Если
эталон вычислять из реестра, проверка сравнит реестр с ним же и перестанет
замечать пропущенную регистрацию — ошибка станет невидимой ровно тогда,
когда она опасна. Поэтому число живёт как константа, отдельно
объявленная для каждой конфигурации: **23 без моста плеера и 24 с ним**,
а наличие моста плеера учитывается явно, а не выводится из реестра.
Проверка сверяет фактическое число записей с этой константой.

## 7. Критерии приёмки

Каждый пункт проверяем и закрыт или не закрыт — без «вроде работает».

**Автопоиск**

1. На временных папках `find_cli` находит программу в каждом из пяти
   источников по отдельности и возвращает верный `from_source`.
2. Порядок соблюдён: при наличии в PATH и в папке приложения побеждает PATH.
3. При двух совпадениях в папке приложения выбран самый свежий по дате **и
   только после проверки, что он запускается**; при равных датах выбор не
   зависит от порядка обхода.
4. Отсутствующая программа возвращает пустой путь и `from_source` =
   `не найдено`, а не исключение. Обёртка `find_cli_path` на том же входе
   возвращает `None`, а не пустую строку: оба вида «нет программы» заданы
   явно и различаются тестом.
5. Чтение `CODEX_CLI_PATH` не падает на битом TOML, на пустом файле и на
   файле с чужими строками.
6. Команда агента не может подставить путь: чужой путь в поиск не попадает.

**Claude**

7. В argv моста нет ни `bypassPermissions`, ни `--dangerously-skip-permissions`,
   ни `--allowedTools` с правом писать; проверяется отдельно и при отсутствии
   сети.
8. Три запрета правки присутствуют в команде: `plan`,
   `--permission-prompts none`, `--disallowedTools` с инструментами правки.
   Проверяется именно набор флагов; полноту защиты он не доказывает — см. 3.2.
9. `stdin` у ребёнка закрыт: заглушка, которая читает stdin, не может
   съесть сообщение протокола — тест с заглушкой, которая читает канал.
10. Разбор ответа закрывает все семь ситуаций контракта 3.4, включая
    `stderr` при нечитаемом JSON и отсутствие `session_id`.
11. Граничные случаи `workspace` из раздела 4 проверены автотестом, включая
    кириллицу, пробелы, `&`, относительный путь и путь длиннее 260 знаков.

**Диагностика**

12. Журнал содержит строку об источнике программы и строку о входе, и не
    содержит ни ключей, ни полных путей к настройкам пользователя.
13. Окно и таблица при отсутствии CLI называют приложение (если оно стоит),
    дают команду установки и не пишут «мост сломан».

### 7.2 Критерии — из ревью 15.10.2026, второе ревью

**Аргументы и запуск**

29. `--disallowedTools` передаётся пятью отдельными элементами argv. Проверка
    двухчастная, и вторая часть важнее первой:
    - **команда** — автотест сверяет точную последовательность элементов argv;
      это ловит опечатку в формате;
    - **эффект** — при наличии настоящего Claude Code выполняется живая
      проверка: команда с просьбой создать файл обязана быть отклонена, а в
      ответе — не «сделано». Пока настоящей CLI на машине нет, этот пункт
      **не закрыт** и помечен как ожидающий живого запуска.

    **Что этот пункт доказывает и что нет — граница формулировки.** Живая
    проверка доказывает ровно одно: при выбранной комбинации аргументов
    создание файла было предотвращено. Она **не** доказывает, что помешало
    именно `--disallowedTools`: с тем же успехом это мог сделать и режим
    `plan`, который по документации тоже не правит исходные файлы. Обе
    причины действуют одновременно, и разделить их одним запретом нельзя.

    Поэтому в отчёте пишется: «при аргументах A, B, C файл создан не был» —
    и не пишется «сработал `--disallowedTools`».

    Чтобы разнести причины, нужен **контрольный прогон**: тот же запрос без
    `--disallowedTools`, с остальными аргументами как были. Тогда возможны
    три исхода, и каждый записывается как есть:

    | контрольный прогон | что можно сказать в отчёте |
    |---|---|
    | файл создан | ограничения вместе работают, вклад `--disallowedTools` подтверждён |
    | файл не создан | достаточно `plan`; `--disallowedTools` остаётся неатрибутированным |
    | прогон неубедителен | причина не установлена, выводов не делаем |

    Контрольный прогон — уточнение, а не отдельный критерий: он выполняется
    только вместе с основным и только при наличии настоящей CLI. Без него
    критерий 29 остаётся закрытым лишь в части «эффект не наблюдался», но не
    в части «какая именно настройка помешала».

    **Даже положительный исход контрольного прогона — свидетельство в одном
    сценарии, а не доказательство вообще.** Вывод «запрет сработал» здесь
    означает ровно одно: при этой версии CLI, этом тексте запроса и этом
    наборе остальных аргументов файл не создан, а без `--disallowedTools` в
    тех же условиях — создан. Ни версия, ни запрос, ни остальные аргументы
    из этого вывода не выносятся.

    Поэтому в отчёте фиксируются: версия CLI, **точный argv обоих прогонов**
    и результат каждого из них. Обобщения вида «запрет не позволяет менять
    файлы» не пишутся: один сценарий не покрывает ни перенаправление вывода,
    ни `find -delete`, ни подпроцессы, перечисленные в 3.2. Вывод,
    перенесённый на другие способы изменения файлов, был бы тем же
    обобщением, от которого мы отказались в строке «файл создан» таблицы
выше.

    Честное ограничение: заглушка не может доказать, что CLI применил запрет.
    Проверка argv доказывает только, что команда собрана верно; применение
    запрета — свойство программы, и доказывается она живым запуском.
30. **`.cmd` и `.bat` для мостов к агентам не используются вообще.**
    Кандидат такого типа отбрасывается на этапе допуска с причиной, и мост
    Claude не запускает такую программу ни при каких аргументах. Отказ
    касается **всех** источников, включая совпадения в PATH: обнаружение
    файла не даёт права на запуск. Проверка идёт **до** вызова `prepare_argv`
    и тем более до `subprocess`: при отказе не запускается ничего, что
    подтверждается заглушкой-«счётчиком запусков» с нулём вызовов.

    Проверяется не только отказ, но и **что вторая команда не выполнилась**:
    заглушка-кандидат при попытке запуска создала бы файл-признак, и тест
    требует, чтобы такого файла не появилось. Это единственная проверка,
    которая отличает «мост отказался» от «мост отказался, а что-то успело
    выполниться». Для `.exe` ограничений нет.

    Отказ сопровождается диагностикой с тремя элементами: какая программа
    найдена, почему она не подходит, и что поставить вместо неё.

    Отдельно проверяется, что отказ не обходится через `prepare_argv`:
    рядом с найденным `.exe` кладётся `.cmd`-обманка, и тест требует, чтобы
    запустилась именно `.exe`, а файл-признак у `.cmd` не появился.
    Лаунчер, передающий в `argv[0]` имя вместо найденного пути, такой тест
    роняет — и это единственный способ поймать обход, который на
    заглушке-«счётчике» сам по себе не виден.
31. Мост не запускает команды входа: ни `claude auth login`, ни
    `codex login`, ни `agent login`. Проверяется весь argv команды проверки
    целиком — ровно три элемента: `["<абсолютный путь к claude.exe>", "auth",
    "status"]`. Правильные слова при лишнем элементе не считаются совпадением:
    это уже другая команда.

**Процессы**

32. По таймауту останавливается дерево процессов, а не только прямой
    процесс. Тест построен так, что заглушка **обязательно успевает создать
    потомка** до срабатывания таймаута: номер потомка пишется в файл, тест
    сначала убеждается, что файл есть и процесс жив, и только потом
    дожидается таймаута. Иначе тест проходит, не проверив самое главное.
    Завершение потомка проверяется **по этому номеру процесса**, а не по
    тексту журнала: журнал может соврать, а процесс — нет. Правило
    распространено на существующие мосты, где есть таймаут.

    Очистка считается выполненной **по проверке процессов, а не по коду
    `taskkill`**: код 0 не доказывает, что всё исчезло. Отдельный случай —
    заглушка, у которой потомок переживает родителя: тест обязан получить
    `ошибка_остановки` с номером оставшегося процесса, а не `таймаут`.

    **Проверяется тот самый процесс, а не просто «процесс с таким номером
    есть».** Номер может быть уже переиспользован другой программой: тогда
    тест увидит живой PID и решит, что очистка не удалась, хотя на самом деле
    убит был другой процесс. Поэтому заглушка пишет в файл не только номер,
    но и время создания процесса и имя образа, а проверка сверяет их вместе с
    номером. Если сверить идентичность не удалось, тест **не считается
    пройденным молча**: он падает с пометкой «не удалось подтвердить, что
    проверяется именно тот процесс», иначе гонка маскировалась бы под
    результат.

**Поиск**

33. PATH перебирается целиком: при нескольких одноимённых программах в
    разных папках PATH берётся первая рабочая, а не первая найденная. Порядок
    задаётся **последовательностью папок PATH**, а не временем изменения
    файлов: более свежая копия в папке, которая стоит в PATH позже, не
    выигрывает. Это отдельное правило, а не частный случай правила о свежести,
    которое действует в папке приложения.
34. Первый источник содержит нерабочий файл, следующий — рабочий: поиск
    находит второй. То же для двух подряд нерабочих в одном источнике, с
    двумя разными причинами.
35. `reason` содержит короткий итог, `attempts` — полный перечень: при
    нескольких отказах подряд ни одна причина не теряется и не перетирает
    другую. В `attempts` различаются три вида записи — «обнаружен»,
    «отклонён политикой типа файла», «проверка запуска выполнена». Отказ в
    допуске не выдаётся за поломку программы, и `reason` при найденной
    рабочей программе не содержит отказ более раннего `.cmd`.

**Диагностика и пути**

36. Фильтр секретов проверен на четырёх случаях: длинное значение, значение
    с переносами строк, значение в URL или в закодированном виде, и сбой
    самого фильтра. При сбое диагностика **не выдаётся** — в ответе остаётся
    только фраза моста.

    Как именно ищется закодированное значение: простой замены исходной
    строки мало. Из известного секрета до ответа строится **набор
    представлений**, и проверяется каждый:
    - как есть;
    - процентно закодированное (все спецсимволы, а не только часть);
    - закодированное с плюсом вместо пробела;
    - с экранированием для HTML, где `&` становится `&amp;`.

    **«При сомнении» означает ровно одно: фильтр не отработал.** Два случая
    различаются, иначе из одной фразы получатся две разные реализации:

    | случай | что известно | что делаем |
    |---|---|---|
    | фильтр отработал, представления построены, совпадений нет | текст проверен по всем обещанным формам | диагностику **показываем** — она уже отфильтрована |
    | фильтр не смог обработать вход, построить представления или закончить проверку | текст проверен частично или никак | диагностику **не выдаём целиком**, остаётся только фраза моста |

    Второй случай важнее первого: непроверенный текст нельзя отдавать как
    проверенный, даже если ни одно известное представление не совпало.

    Чего фильтр **не** делает и почему: он не ищет base64 и не пытается
    декодировать произвольный текст — это безграничная работа и ложные
    срабатывания. Отдельно проверяется, что фильтр на нестроковых данных
    (например, на байтах от кривой кодировки) не падает, а возвращает
    «не разбираю» — и тогда текст не выводится вовсе.
37. Ошибки `Path.resolve()` — права, петля ссылок, длина — дают понятный отказ,
    а не необработанное исключение.
38. `session_id` при ошибке сохранён для диагностики, но статус остаётся
    ошибочным, и мост не предлагает продолжить разговор как рабочую сессию.

## 8. Проверка

**Сверка заглушек с настоящим выводом.** Образцы хранятся в репозитории как
данные теста и делятся на три группы — смешивать их нельзя, они проверяют
разное.

**Группа 1. Документированные примеры Claude.** Проверяют разбор ожидаемого
JSON и форму команды.

| образец | источник | что проверяет |
|---|---|---|
| `{"result": "...", "session_id": "abc-123", "total_cost_usd": 0.01}` | пример из `/headless`, `jq -r '.session_id'` | извлечение `result` и `session_id` |

**Группа 2. Зафиксированные реальные ответы программ.** Проверяют
классификацию известных состояний. Сняты 15.10.2026.

| образец | источник | что проверяет |
|---|---|---|
| `Not logged in`, код 1 | живой вывод `codex login status` | «входа нет» у Codex |
| `Logged in using ChatGPT`, код 0 | тот же | «вход есть» |
| `Not authenticated`, код 1 | раздел Troubleshooting документации Cursor | отказ во входе у Cursor |
| `{"error":{"code":"invalid_refresh_token"}, "message":"Could not validate your refresh token"}` | живой вывод `codex exec` | подсказка «войди» |
| `API ответил 401 … "code": "invalid_api_key"` | живой вызов `api.openai.com` | отсутствие ключа в тексте |
| `Not connected to Spotify. Run the authenticate tool…` | живой вызов пакета | подсказка о входе у Spotify |

**Группа 3. Искусственные негативные примеры.** Проверяют то, чего не было на
машине: нет JSON, пустой `result`, нет `session_id`, ненулевой код с текстом
только в `stderr`, ошибка запуска, таймаут, повреждённые данные, кандидат
нулевого размера и кандидат, который не запускается.

К каждому образцу пишется: источник, дата, версия программы (если известна),
ожидаемая классификация и какие поля гарантированно присутствуют.

**Проверяем смысл, а не букву.** Тест сравнивает структуру и ожидаемую
классификацию — признаки входа, отказ, код, наличие полей. Смена
формулировки при неизменной структуре **не** должна ронять тест: программа
переписала текст, а не формат ответа. Образцы остаются регрессионными
данными, но требовать их дословного постоянства было бы требованием
заморозить чужие формулировки.

**Живая проверка — три утверждения, и они не смешиваются.** 15.10.2026
доказано ровно одно: подключение Unity работает (48 инструментов,
`opencode mcp list` показал `✓ unity connected`). Это подтверждает
конкретное соединение в конкретный момент и **не** доказывает нижеследующее:

| утверждение | чем доказывается | чем не доказывается |
|---|---|---|
| подключение Unity работает | живой прогон 15.10.2026 | что автопоиск выбрал верный источник |
| автопоиск Codex назвал верный источник | журнал запуска плюс проверка пути | что все пять источников обойдены, — это тест на временных папках |
| остальные мосты не откатились | регрессионные тесты A5 | что одно удачное подключение говорит о них что-либо — не говорит |

Формулировка «мост работает» без указания, **что именно** работает, в отчёте
не допускается: из одного успешного соединения нельзя вывести ни выбор
источника, ни отсутствие регрессий.

Cursor и Claude — только заглушками: настоящих CLI на машине нет.

**Формулировка вывода о Claude.** Проверка на живой CLI доказывает, что
создание файла при выбранной комбинации аргументов предотвращено, и не
доказывает, что помешало именно `--disallowedTools`: причиной мог оказаться
режим `plan`. В отчёте утверждается первое; второе пишется как
неатрибутированное, пока нет контрольного прогона (критерий 29). Смешивать
эти два утверждения нельзя: отчёт читают потом, когда забываешь, что было
замерено, а принимают решения по нему.

**Самопроверка.** Новый раздел рядом с 5ж. Ожидаемое число серверов —
**одна именованная константа на каждую конфигурацию**, а не числа в трёх
местах: 23 без моста плеера и 24 с ним. Проверяются **обе**
конфигурации, и каждая проверяет не только совпадение числа, но и
пропущенную регистрацию (раздел 6, часть B3 плана).

**Карта приёмки: что, чем, по какому критерию и что считается доказанным.**
Дословно все 42 критерия здесь не повторяются — это обзор, а не копия.

| проверка | способ | критерий | что считается доказанным |
|---|---|---|---|
| поиск в пяти источниках | автотест на временных папках | 1–6, 14–18, 33–35 | механика выбора источника, порядка и отказов |
| порядок PATH не зависит от даты файла | две рабочие копии в разных папках PATH | 33 | приоритеты системы не переписаны нашими |
| отказ пакетных файлов | заглушка-счётчик плюс `.cmd`-обманка рядом с `.exe` | 30 | ничего не запущено, обход через `prepare_argv` невозможен |
| три исхода таймаута | три заглушки: потомок ушёл сам, потомок жив, потомок пережил родителя | 25, 32 | статусы различимы, очистка подтверждается по живости процесса |
| опознание процесса | сверка PID, имени образа и времени создания | 32 | проверяется именно тот процесс, гонка PID не маскируется |
| журнал не растёт | счётчик строк до и после серии вызовов | 12 | события логируются, обычные вызовы не логируются |
| фильтр секретов | четыре случая плюс каждое представление, в ответе и в файле журнала | 26, 36 | секрет не уходит никуда, сбой фильтра не выдаёт ничего |
| регрессия существующих мостов | запуск Spotify и второго моста прежним способом | 19, 41 | общий модуль не изменил поведение старых потребителей |
| независимый эталон мостов | два прогона: без моста плеера и с ним | 41 | пропущенная регистрация обнаруживается в каждой конфигурации |
| ограничения Claude | автотест `argv` плюс живой запуск с контрольным прогоном | 29, 39, 42 | команда собрана верно; вклад флага — только по результату контрольного прогона |

Всё, чего в этой таблице нет, проверяется соответствующим пунктом части A
или B плана; таблица не заменяет критерии, а показывает, где искать.

## 9. Границы задачи

Вне её: перенос в `opencode-base-main`, установка чего-либо, авторизация,
выдача ключей, поиск трека по названию, мост плеера (отдельная задача, своя
спецификация от 15.10.2026).

Внутри две независимые части, порядок значения не имеет: автопоиск чинит
уже сломанный случай с Codex, мост Claude добавляет новый сервер. Если одна
не сложится, вторая всё равно даёт пользу.

Оговорка про независимость: общий помощник автопоиска лежит в
`bridge_common.py`, то есть в коде, которым пользуются все мосты, а не
только Claude. Поэтому его правка обязана сохранять обратную совместимость
с мостами, к Claude отношения не имеющими: старый вызов `resolve_exe`
продолжает работать как раньше, а новая функция добавляется рядом, а не
вместо. Ошибка в одной части не должна ломать ни регистрацию, ни запуск
другой.

**Протокол будущей живой проверки запретов живёт не здесь:** он в критериях
29 и 42 и в части C плана работ, чтобы не оказалось двух правд о порядке
шагов.

## 10. Что останется недоказанным

- Настоящий текст ответов `agent status` и `claude auth status`: программ на
  машине нет, механизм доказывается заглушкой.
- Живой ответ Claude невозможен без Claude Code.
- **Заглушки доказывают механику, а не совместимость.** Ни один тест этой
  задачи не говорит, что мост заработает с настоящими версиями Codex,
  Cursor и Claude: образцы берутся из документации и из живых выводов тех
  версий, что стоят на машине. Совместимость проверяется только после
  установки настоящей CLI.

Отдельно, до живой проверки остаются неизвестными:

- фактическое поведение установленной версии Claude Code с выбранным набором
  аргументов;
- реальная работа входа через установленное приложение Claude;
- обработка ошибок запуска на целевой машине;
- фактическое поведение при продолжении сессии через `--resume`;
- совместимость с текущими версиями всех мостов, пользующихся общим
  автопоиском;
- **настоящее различение кодов `claude auth status`**: что означает код `1`
  на установленной версии и отличается ли он от прочих ненулевых. Тест с
  заглушкой доказывает, что наш код правильно классифицирует заданный код, но
  не доказывает, что CLI использует этот код именно в таком смысле;
- **реальное подтверждение остановки дерева процессов.** Заглушка доказывает,
  что реализация верно классифицирует сценарий с оставшимся потомком, но не
  даёт гарантии, что очистка сработает на любом процессе и в любом состоянии
  Windows;
- результат живой проверки ограничений Claude **вместе с контрольным
  прогоном**: пока совместимой CLI нет, не выполнено ни то, ни другое, и
  отсутствие контрольного прогона не считается запретом на вывод;
- и — по всей задаче — что именно сделает модель, получив запрос на правку
  файлов. Механизмы ограничения известны, поведение модели нет.

**Два разных «недоказанных», и смешивать их нельзя.** Первое — неизвестное
поведение чужой программы: что сделает установленный Claude Code, какой код
вернёт CLI. Второе — недоказанность нашего собственного кода: заглушка может
не покрывать сценарий, который мы не предусмотрели. Первое закрывается
живым запуском на настоящей программе, второе — расширением тестов. Отчёт
обязан называть, что из этого перед ним.
