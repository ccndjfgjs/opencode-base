# Написание планов

## Принцип

Пиши исчерпывающие планы реализации, исходя из допущения, что у инженера ноль контекста о нашей кодовой базе и сомнительный вкус. Документируй всё, что ему нужно: какие файлы трогать в каждой задаче, код, тестирование, документацию, которую, возможно, надо проверить, как это тестировать. Выдавай весь план как задачи размером с укус. DRY. YAGNI. TDD. Частые коммиты.

Считай, что это умелый разработчик, но почти ничего не знающий о нашем инструментарии и предметной области. Считай, что он плохо знает хороший дизайн тестов.

**Объяви в начале:** «Использую скилл writing-plans для создания плана реализации».

**Сохраняй планы в:** `docs/plans/YYYY-MM-DD-<имя-функции>.md`
- (Предпочтения пользователя о месте хранения планов важнее этого значения по умолчанию)

## Проверка масштаба

Если спецификация покрывает несколько независимых подсистем, она должна была быть разбита на подпроекты во время мозгового штурма. Если этого не случилось, предложи разбить на отдельные планы — по одному на подсистему. Каждый план должен самостоятельно давать работающее, тестируемое ПО.

## Структура файлов

Прежде чем определять задачи, распиши, какие файлы будут созданы или изменены и за что каждый отвечает. Здесь фиксируются решения о декомпозиции.

- Проектируй блоки с чёткими границами и хорошо определёнными интерфейсами. У каждого файла одна ответственность.
- Ты рассуждаешь лучше о коде, который помещается в контекст целиком, и правки надёжнее, когда файлы сфокусированы. Предпочитай маленькие сфокусированные файлы большим, делающим слишком много.
- Файлы, меняющиеся вместе, должны жить вместе. Дели по ответственности, а не по техническому слою.
- В существующих кодовых базах следуй устоявшимся шаблонам. Если в кодовой базе приняты большие файлы, не перекраивай в одностороннем порядке — но если файл, который ты меняешь, стал неуклюжим, включить его разделение в план разумно.

Эта структура определяет декомпозицию задач. Каждая задача должна давать самостоятельные изменения, осмысленные отдельно.

## Правильный размер задач

Задача — наименьшая единица, несущая собственный цикл тестирования и заслуживающая свежего взгляда проверяющего. При разметке границ задач: подготовку, конфигурацию, каркас и шаги документации вливай в ту задачу, чей результат их требует; разделяй только там, где проверяющий мог бы осмысленно отклонить одну задачу, одобрив соседнюю. Каждая задача заканчивается независимо проверяемым результатом.

## Мелкость шагов

**Каждый шаг — одно действие (2–5 минут):**
- «Напиши падающий тест» — шаг
- «Запусти его и убедись, что падает» — шаг
- «Реализуй минимальный код, чтобы тест прошёл» — шаг
- «Запусти тесты и убедись, что проходят» — шаг
- «Закоммить» — шаг

## Заголовок документа плана

**Каждый план ОБЯЗАН начинаться с такого заголовка:**

```markdown
# План реализации: [Имя функции]

> **Для агентов-исполнителей:** ОБЯЗАТЕЛЬНЫЙ СКИЛЛ: используй executing-plans
> для реализации этого плана задача за задачей. Шаги используют синтаксис
> чекбоксов (`- [ ]`) для отслеживания.

**Цель:** [Одно предложение: что это строит]

**Архитектура:** [2–3 предложения о подходе]

**Стек технологий:** [Ключевые технологии/библиотеки]

**Спецификация:** [путь к документу дизайна, который реализует этот план]

## Глобальные ограничения

[Общие требования проекта из спецификации — версии, ограничения зависимостей,
правила именования, требования платформы — по одной строке, с точными
значениями, скопированными из спецификации. Требования каждой задачи неявно
включают этот раздел.]

---
```

## Структура задачи

````markdown
### Задача N: [Имя компонента]

**Файлы:**
- Создать: `точный/путь/к/файлу.py`
- Изменить: `точный/путь/к/существующему.py:123-145`
- Тест: `tests/точный/путь/к/тесту.py`

**Интерфейсы:**
- Потребляет: [что задача использует из предыдущих задач — точные сигнатуры]
- Производит: [на что полагаются следующие задачи — точные имена функций,
  типы параметров и возврата. Исполнитель задачи видит только свою задачу;
  этот блок — как он узнаёт имена и типы соседних задач.]

- [ ] **Шаг 1: напиши падающий тест**

```python
def test_конкретное_поведение():
    result = функция(вход)
    assert result == ожидаемое
```

- [ ] **Шаг 2: запусти тест и убедись, что он падает**

Запуск: `pytest tests/путь/тест.py::test_имя -v`
Ожидание: FAIL с «function not defined»

- [ ] **Шаг 3: напиши минимальную реализацию**

```python
def функция(вход):
    return ожидаемое
```

- [ ] **Шаг 4: запусти тест и убедись, что он проходит**

Запуск: `pytest tests/путь/тест.py::test_имя -v`
Ожидание: PASS

- [ ] **Шаг 5: закоммить**

```bash
git add tests/путь/тест.py src/путь/файл.py
git commit -m "feat: добавить конкретную функциональность"
```
````

## Никаких заглушек

Каждый шаг должен содержать реальное содержимое, нужное инженеру. Это **провалы плана** — никогда не пиши так:
- «УТОЧНИТЬ», «TODO», «реализовать позже», «заполнить деталями»
- «Добавь подходящую обработку ошибок» / «добавь валидацию» / «обработай краевые случаи»
- «Напиши тесты для вышеизложенного» (без реального кода теста)
- «Похоже на задачу N» (повтори код — исполнитель может читать задачи не по порядку)
- Шаги, описывающие что делать без «как» (для кодовых шагов нужны блоки кода)
- Ссылки на типы, функции или методы, не определённые ни в одной задаче

## Самопроверка

Написав полный план, посмотри на спецификацию свежим взглядом и сверь план с ней. Это чек-лист, который ты выполняешь сам.

**1. Покрытие спецификации:** просмотри каждый раздел/требование спецификации. Можешь указать задачу, которая его реализует? Перечисли пробелы.

**2. Поиск заглушек:** поищи в плане красные флаги — любой шаблон из раздела «Никаких заглушек». Исправь.

**3. Согласованность типов:** совпадают ли типы, сигнатуры методов и имена свойств в поздних задачах с определёнными в ранних? Функция `очиститьСлои()` в задаче 3 и `очиститьВсеСлои()` в задаче 7 — это баг.

Нашёл проблемы — исправь на месте. Нашёл требование спецификации без задачи — добавь задачу.

## Передача в выполнение

Сохранив план, предложи выбор способа выполнения:

**«План готов и сохранён в `docs/plans/<файл>.md`. Два варианта выполнения:**

**1. По задачам с проверками (рекомендуется)** — каждую задачу выполняю отдельно, показываю результат после каждой для вашего контроля

**2. Сплошное выполнение** — выполняю все задачи подряд в этой сессии, с контрольными точками

**Какой подход?»**

**Если выбран вариант 1:** используй скилл executing-plans, выполняя задачи по одной с показом результата после каждой.

**Если выбран вариант 2:** используй скилл executing-plans, пакетное выполнение с контрольными точками для проверки.
