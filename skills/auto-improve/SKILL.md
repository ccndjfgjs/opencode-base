# Улучшение текста через auto-improve

## Ключ судьи: спроси человека, а не отчитайся о препятствии

Цикл не запустится без ключа Gemini. Это **не повод писать «не могу,
нужен ключ»** — это повод **спросить ключ у человека сразу**.

Порядок, когда ключа нет:

1. `python tools/dbapp/auto_improve.py check` — покажет, что не хватает.
2. Спроси ключ у человека прямо и коротко. Скажи ровно это:
   - ключ Gemini для aistudio.google.com/apikey;
   - он ляжет файлом `auto-improve-key.txt` рядом с настройками opencode,
     в репозиторий не попадёт и в журнал не напечатается;
   - нужен для роли судьи, а мутатор по умолчанию тот же.
3. Внеси его командой `auto_improve.py key`. Команда читает ключ скрыто.
4. `check` снова — должно стать «Готово к запуску».

**Ключ нельзя** выдумывать, брать из чужих настроек, вписывать в
команду аргументом или показывать в ответе. Перенаправленный ввод
команда принимает — значит можно передать ключ так:

```bash
printf '%s' "$KEY" | python tools/dbapp/auto_improve.py key
```

Если человек ключ давать не хочет — скажи честно, что цикл не пойдёт, и
предложи улучшить текст вручную. Молча подставлять чужой ключ нельзя.

## Зависимости ставит программа, ключ — это ваш

Что нужно этому инструменту, решает модуль, а не человек:

| что нужно | кто доставляет |
|---|---|
| копия скрипта автора | уже лежит в проекте |
| `git` | модуль ставит сам через winget (`Git.Git`) |
| `requests` | модуль ставит сам: `pip install requests` |
| **ключ Gemini** | **только человек** — его нельзя скачать |

То есть при нажатии галочки программа сама дотягивает всё, что можно
дотянуть, и отказывается только на ключе — с прямым текстом, что его надо
вписать. Если `git` или `requests` уже есть, повторно ничего не ставится.

Проверкам ставить запрещено: переменная `OPENCODE_NO_AUTO_INSTALL`.

## Судья — только Gemini, и вот почему

Скрипт автора ходит **только** в
`https://generativelanguage.googleapis.com` — адрес зашит в коде, другой
он не берёт, формат запроса тоже Gemini. Проверено чтением копии
`tools/thirdparty/auto-improve/improve.py`, живьёй проверкой на
15.10.2026: переменной для другого адреса у него нет.

Поэтому модель судьи выбирается **из Gemini**:

| роль | по умолчанию | как сменить |
|---|---|---|
| судья | `gemini-flash-latest` | `IMPROVE_EVALUATOR` в окружении |
| мутатор | `gemini-flash-latest` | `IMPROVE_MUTATOR` в окружении |

Предложи человеку выбор модели (`gemini-flash-latest` — быстрее и
дешевле, `gemini-pro-latest` — вдумчивее), но **не выбирай за него
модель молча**: скажи, какая стоит по умолчанию, и спроси, менять ли.

Провайдеры из настроек opencode (`dahl`, `chad`, `qwencloud`, `genapi`)
судьёй быть **не могут** — они говорят по другому протоколу. Если человек
просит именно их, скажи это прямо и предложи Gemini, а не делай вид, что
получится.

## Когда брать

- Просят **измеримо** лучше: письмо, лендинг, промпт, README, описание API,
  конфиг, письмо клиенту, — и «лучше» можно сформулировать словами.
- Есть рубрика (или её не страшно вывести из самого файла): цикл улучшает
  ровно то, что написано в критериях.
- Есть **отдельная ветка или копия проекта**: цикл сам делает коммиты, и
  это его замысел, а не побочный эффект.

## Когда не брать

- **Файл не в git-репозитории.** Скрипт хранит улучшения коммитами в ветке
  `improve/<тег>`; без репозитория он работать не будет. Скажи это прямо и
  предложи сначала сделать `git init` и первый коммит — или улучшить текст
  вручную.
- **Незакоммиченные правки в рабочем дереве.** Скрипт делает `git add -A`,
  и твои несохранённые изменения уедут в новую ветку. Сначала закоммить или
  отложи их.
- **Нет ключа судьи и нет сети к Gemini.** Ключ лежит файлом
  `auto-improve-key.txt` рядом с настройками opencode (вносится командой
  `auto_improve.py key`, ключ не печатается) или берётся из `GEMINI_API_KEY`.
  **Ключ не печатать в ответ, не вставлять в команды и не передавать в
  аргументах.**
- **Нет библиотеки `requests` у Python.** Программа об этом скажет словами;
  ставить её за человека не надо — предложи команду
  `"<python>" -m pip install requests`.

## Как это устроено

```
auto_improve.py run <файл> [тег] [рубрика] [цель]
                 │
                 ▼
   improve.py (копия автора в tools/thirdparty/auto-improve)
     правки → оценка отдельной моделью-судьёй по рубрике → попарное
     сравнение с текущей версией → только выигравшее остаётся
                 │
                 ▼
   ветка improve/<тег> в репозитории файла — это журнал улучшений
   <настройки opencode>/auto-improve-data/ — журнал хода и вывод циклов
```

Рубрика — markdown-файл с размерами, суммарно 100 баллов. Свои рубрики
можно не писать: без рубрики скрипт выведет её из файла (и сохранит рядом
с журналом хода, чтобы было видно, по каким критериям шла работа).

## Как запускать

Всё делается **командой**. Отдельного окна с кнопками больше нет: тот же
смысл переехал сюда.

```
python tools/dbapp/auto_improve.py status            # готовность: ключ, git, requests
python tools/dbapp/auto_improve.py check             # то же, код 0 — готово
python tools/dbapp/auto_improve.py key               # вписать ключ судьи (не печатается)
python tools/dbapp/auto_improve.py run <файл> [тег] [рубрика] [цель]
python tools/dbapp/auto_improve.py history <тег>     # ход запуска
python tools/dbapp/auto_improve.py tags              # какие запуски вообще были
python tools/dbapp/auto_improve.py install           # включить отметку в настройках
python tools/dbapp/auto_improve.py remove            # снять отметку
```

Ключ судьи вносится **только** командой `key`: она спрашивает его скрыто и
нигде не печатает. Не передавай ключ аргументом — он останется в истории
команд. Если ключ уже лежит в переменной `GEMINI_API_KEY`, ничего вносить
не нужно, `status` это покажет.

`run` без рубрики выведет её из самого файла. Перед запуском предупреди
человека про ветку и про расход токенов — это теперь твоя обязанность,
окно раньше делало это само.

Порядок, ключи и переменные — из README автора: `--artifact`, `--tag`,
`--criteria`, `--goal`, `--max-iterations` (по умолчанию 10), `--candidates`
(3), `--eval-runs` (2), `--threshold` (90). Модели — `IMPROVE_MUTATOR` и
`IMPROVE_EVALUATOR`, по умолчанию `gemini-flash-latest`.

## Правила

- **Только отдельная ветка.** Скрипт сам создаёт `improve/<тег>` и коммитит
  туда; основную ветку он не трогает, но `git add -A` утащит всё, что не
  закоммичено. Прежде чем запускать — проверь `git status`.
- **Судья — тоже нейросеть.** «Выиграл сравнение» не значит «стало
  правильно». Каждый шаг — отдельный коммит: покажи человеку, что изменилось
  (`git diff <основная-ветка> improve/<тег> -- <файл>`), и не выдавай
  улучшение за истину.
- **Числа автора — не факт.** Примеры роста из его README («68 → 76»,
  «48 → 52 → 56») — заявления автора, независимо не проверены. Свои числа
  бери из журнала хода конкретного запуска.
- **Ключ и токены.** Цикл тратит токены; на бесплатном ключе упирается в
  лимиты. Ключ не выводить ни в ответ, ни в команды, ни в файлы репозитория.
- **Не MCP.** Это сторонний Python-скрипт, а не сервер: в
  `mcp-registry.json` его нет и быть не должно.

## Частые ошибки

- «Улучши файл» без ветки → чужие незакоммиченные правки уезжают в
  `improve/<тег>`. Скажи об этом до запуска.
- Ожидание «файл перепишется красиво целиком» → цикл делает **точечные**
  правки; если рубрика не описывает желаемое, результат будет не тот.
- Запуск на файле вне репозитория → скрипт не найдёт git-корень. Проверь
  заранее (`auto_improve.py status` и `git status`).
