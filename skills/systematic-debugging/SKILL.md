# Системная отладка

## Принцип

**Главное правило: всегда находи корневую причину, прежде чем пытаться исправить. Лечение симптомов — провал.**

Нарушение буквы этого процесса — нарушение духа отладки.

## Железный закон

```
НИКАКИХ ИСПРАВЛЕНИЙ БЕЗ ПРЕДВАРИТЕЛЬНОГО РАССЛЕДОВАНИЯ КОРНЕВОЙ ПРИЧИНЫ
```

Если фаза 1 не завершена — предлагать исправления нельзя.

## Когда применять

При ЛЮБОЙ технической проблеме:
- упавшие тесты
- баги в рабочем окружении
- неожиданное поведение
- проблемы производительности
- ошибки сборки
- проблемы интеграции

**Применять ОСОБЕННО, когда:**
- нехватка времени (в экстренных ситуациях хочется угадать)
- «одно быстрое исправление» кажется очевидным
- уже попробовали несколько исправлений
- предыдущее исправление не сработало
- проблема до конца не понятна

**Не пропускать, когда:**
- проблема кажется простой (у простых багов тоже есть корневая причина)
- торопитесь (спешка гарантирует переделку)
- начальник хочет «прямо сейчас» (системный подход быстрее хаотичных попыток)

## Четыре фазы

Каждую фазу ОБЯЗАТЕЛЬНО завершить, прежде чем переходить к следующей.

### Фаза 1: поиск корневой причины

**ПРЕЖДЕ чем пытаться что-либо исправить:**

1. **Внимательно прочитай сообщения об ошибках**
   - не проскальзывайте мимо ошибок и предупреждений
   - они часто содержат точное решение
   - читайте стек-трейсы полностью
   - отмечайте номера строк, пути файлов, коды ошибок

2. **Воспроизведи стабильно**
   - можете ли вы вызвать ошибку надёжно?
   - какие точные шаги?
   - происходит ли каждый раз?
   - если не воспроизводится → соберите больше данных, не гадайте

3. **Проверьте недавние изменения**
   - что изменилось и могло это вызвать?
   - git diff, недавние коммиты
   - новые зависимости, изменения конфигурации
   - различия окружения

4. **Соберите доказательства в системах из нескольких компонентов**

   **КОГДА система состоит из нескольких компонентов (CI → сборка → подпись, API → сервис → база):**

   **ПРЕЖДЕ чем предлагать исправления, добавьте диагностическое инструментирование:**
   ```
   Для КАЖДОЙ границы компонентов:
     - логируйте, какие данные входят в компонент
     - логируйте, какие данные выходят из компонента
     - проверьте передачу окружения/конфигурации
     - проверьте состояние на каждом слое

   Запустите один раз, чтобы получить доказательства, ГДЕ ломается
   ЗАТЕМ проанализируйте доказательства и определите сбойный компонент
   ЗАТЕМ исследуйте именно этот компонент
   ```

5. **Проследите поток данных**

   **КОГДА ошибка глубоко в стеке вызовов:**
   - откуда берётся плохое значение?
   - кто вызвал это с плохим значением?
   - трассируйте вверх, пока не найдёте источник
   - исправляйте в источнике, а не в симптоме

### Фаза 2: анализ шаблона

**Найдите шаблон до исправления:**

1. **Найдите рабочие примеры**
   - найдите похожий работающий код в той же кодовой базе
   - что работает похоже на то, что сломано?

2. **Сравните с эталонами**
   - если реализуете паттерн — прочитайте эталонную реализацию ПОЛНОСТЬЮ
   - не просматривайте по диагонали — читайте каждую строку
   - поймите паттерн до конца, прежде чем применять

3. **Определите различия**
   - чем отличается работающее от сломанного?
   - перечислите каждое различие, каким бы мелким оно ни было
   - не предполагайте «это не может быть важно»

4. **Поймите зависимости**
   - какие ещё компоненты нужны?
   - какие настройки, конфигурация, окружение?
   - какие допущения делаются?

### Фаза 3: гипотеза и проверка

**Научный метод:**

1. **Сформулируйте одну гипотезу**
   - ясно скажите: «Я думаю, корневая причина — X, потому что Y»
   - запишите её
   - конкретно, не расплывчато

2. **Проверьте минимально**
   - внесите САМОЕ МАЛЕНЬКОЕ изменение для проверки гипотезы
   - одна переменная за раз
   - не исправляйте несколько вещей сразу

3. **Проверьте результат, прежде чем продолжать**
   - сработало? Да → фаза 4
   - не сработало? Сформулируйте НОВУЮ гипотезу
   - НЕ наслаивайте новые исправления поверх

4. **Когда не понимаете**
   - скажите «Я не понимаю X»
   - не притворяйтесь, что знаете
   - попросите помочь
   - исследуйте дальше

### Фаза 4: реализация

**Исправьте корневую причину, а не симптом:**

1. **Создайте падающий тест**
   - простейшее воспроизведение
   - автоматический тест, если возможно
   - разовый тест-скрипт, если нет фреймворка
   - ДОЛЖЕН существовать до исправления
   - используйте скилл `test-driven-development` для написания правильных падающих тестов

2. **Реализуйте одно исправление**
   - устраните найденную корневую причину
   - ОДНО изменение за раз
   - никаких улучшений «раз уж я здесь»
   - никакой связанной рефакторинга

3. **Проверьте исправление**
   - тест теперь проходит?
   - другие тесты не сломались?
   - проблема реально решена?
   - используйте скилл `verification-before-completion`, прежде чем заявлять об успехе

4. **Если исправление не сработало**
   - СТОП
   - посчитайте: сколько исправлений уже попробовано?
   - если < 3: вернитесь к фазе 1, переанализируйте с новой информацией
   - **если ≥ 3: СТОП и поставьте под вопрос архитектуру (шаг 5 ниже)**
   - НЕ пытайтесь сделать исправление №4 без обсуждения архитектуры

5. **Если 3+ исправления провалились: поставьте под вопрос архитектуру**

   **Признаки архитектурной проблемы:**
   - каждое исправление вскрывает новое общее состояние/связанность/проблему в другом месте
   - исправления требуют «массовой рефакторинга»
   - каждое исправление создаёт новые симптомы в других местах

   **СТОП и спросите о фундаменте:**
   - звучит ли этот паттерн в принципе?
   - не держимся ли мы за него по инерции?
   - может, нужно переделать архитектуру, а не лечить симптомы?

   **Обсудите с человеком, прежде чем пытаться исправлять дальше.**

   Это не «неправильная гипотеза» — это неправильная архитектура.

## Красные флаги — СТОП и вернитесь к процессу

Если ловите себя на мыслях:
- «быстро поправлю, разберусь потом»
- «просто попробую поменять X и посмотрю, что будет»
- «внесу несколько изменений и прогоню тесты»
- «пропущу тест, проверю вручную»
- «наверное, это X, исправлю это»
- «до конца не понимаю, но может сработать»
- «в паттерне сказано X, но я сделаю по-своему»
- «вот основные проблемы: [список исправлений без расследования]»
- предлагаете решения до трассировки потока данных
- **«ещё одна попытка исправления» (когда уже 2+ провалились)**
- **каждое исправление вскрывает новую проблему в другом месте**

**ВСЁ это означает: СТОП. Вернитесь к фазе 1.**

**Если 3+ исправлений провалились:** поставьте под вопрос архитектуру (см. фазу 4, шаг 5).

## Типичные самооправдания

| Отговорка | Реальность |
|-----------|------------|
| «Проблема простая, процесс не нужен» | У простых проблем тоже есть корневая причина. Процесс быстр для простых багов. |
| «Экстренная ситуация, нет времени на процесс» | Системная отладка БЫСТРЕЕ хаотичного метода тыка. |
| «Сначала попробую это, потом расследую» | Первое исправление задаёт шаблон. Делайте правильно с начала. |
| «Тест напишу после подтверждения, что фикс работает» | Непроверенные исправления не закрепляются. Тест сначала доказывает их. |
| «Несколько исправлений сразу сэкономят время» | Невозможно изолировать, что сработало. Порождает новые баги. |
| «Эталон слишком длинный, адаптирую паттерн» | Частичное понимание гарантирует баги. Читайте полностью. |
| «Вижу проблему, исправляю» | Видеть симптомы ≠ понимать корневую причину. |
| «Ещё одна попытка» (после 2+ провалов) | 3+ провала = архитектурная проблема. Ставьте паттерн под вопрос, а не исправляйте снова. |

## Краткая справка

| Фаза | Ключевые действия | Критерий успеха |
|------|-------------------|-----------------|
| **1. Корневая причина** | Читать ошибки, воспроизвести, проверить изменения, собрать доказательства | Понять ЧТО и ПОЧЕМУ |
| **2. Шаблон** | Найти рабочие примеры, сравнить | Определить различия |
| **3. Гипотеза** | Сформулировать теорию, минимально проверить | Подтверждена или новая гипотеза |
| **4. Реализация** | Создать тест, исправить, проверить | Баг решён, тесты проходят |

## Когда процесс показывает «корневой причины нет»

Если системное расследование показывает, что проблема действительно экологическая, зависит от таймингов или внешняя:

1. Процесс завершён
2. Задокументируйте, что исследовали
3. Реализуйте подходящую обработку (повтор, таймаут, сообщение об ошибке)
4. Добавьте мониторинг/логирование для будущих расследований

**Но:** в 95% случаев «нет корневой причины» = незавершённое расследование.
