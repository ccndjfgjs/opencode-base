# Разработка через тестирование (TDD)

## Принцип

Сначала напиши тест. Убедись, что он падает. Напиши минимальный код, чтобы он прошёл.

**Главное правило: если ты не видел, как тест падает, ты не знаешь, проверяет ли он то, что нужно.**

Нарушение буквы этих правил — нарушение их духа.

## Железный закон

```
НИ СТРОКИ ПРОДАКШЕН-КОДА БЕЗ СНАЧАЛА ПАДАЮЩЕГО ТЕСТА
```

Написал код до теста? Удали его. Начни заново.

**Без исключений:**
- не оставляй его «как справочник»
- не «адаптируй» его во время написания тестов
- не подглядывай в него
- «удалить» значит удалить

Реализуй заново, отталкиваясь от тестов. Точка.

## Когда применять

**Всегда:**
- новые функции
- исправления багов
- рефакторинг
- изменения поведения

**Исключения (спроси у человека):**
- одноразовые прототипы
- сгенерированный код
- файлы конфигурации

Думаешь «пропущу TDD, только этот раз»? Остановись. Это самооправдание.

## Цикл: КРАСНЫЙ — ЗЕЛЁНЫЙ — РЕФАКТОРИНГ

### КРАСНЫЙ — напиши падающий тест

Напиши один минимальный тест, показывающий, что должно происходить.

**Хорошо** (понятное имя, проверяет реальное поведение, одна вещь):
```typescript
test('повторяет неудавшуюся операцию 3 раза', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

**Плохо** (расплывчатое имя, проверяет мок, а не код):
```typescript
test('retry works', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```

**Требования:**
- одно поведение
- понятное имя
- реальный код (без моков, если их можно избежать)

### Проверка КРАСНОГО — убедись, что тест падает

**ОБЯЗАТЕЛЬНО. Никогда не пропускай.**

```bash
npm test путь/к/тесту.test.ts
```

Убедись:
- тест падает (а не ломается с ошибкой)
- сообщение об ошибке ожидаемое
- падает из-за отсутствующей функциональности (не из-за опечаток)

**Тест проходит?** Ты тестируешь существующее поведение. Исправь тест.
**Тест ломается с ошибкой?** Почини ошибку, перезапусти, пока тест не начнёт падать правильно.

### ЗЕЛЁНЫЙ — минимальный код

Напиши простейший код, чтобы тест прошёл.

**Хорошо** (ровно столько, чтобы тест прошёл):
```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```

**Плохо** (переусложнено, «на будущее»):
```typescript
async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: {
    maxRetries?: number;
    backoff?: 'linear' | 'exponential';
    onRetry?: (attempt: number) => void;
  }
): Promise<T> {
  // YAGNI
}
```

Не добавляй функции, не рефактори другой код, не «улучшай» сверх теста.

### Проверка ЗЕЛЁНОГО — убедись, что тест проходит

**ОБЯЗАТЕЛЬНО.**

Убедись:
- тест проходит
- другие тесты тоже проходят
- вывод чистый (без ошибок и предупреждений)

**Тест падает?** Чини код, а не тест.
**Другие тесты падают?** Чини сейчас же.

### РЕФАКТОРИНГ — наведи порядок

Только после зелёного:
- убери дублирование
- улучши имена
- выдели вспомогательные функции

Тесты остаются зелёными. Новое поведение не добавляй.

### Повторяй

Следующий падающий тест — для следующей функции.

## Хорошие тесты

| Качество | Хорошо | Плохо |
|----------|--------|-------|
| **Минимальный** | Одна вещь. Есть «и» в имени? Раздели. | `test('проверяет email и домен и пробелы')` |
| **Понятный** | Имя описывает поведение | `test('test1')` |
| **Показывает намерение** | Демонстрирует желаемый API | Скрывает, что код должен делать |

## Типичные самооправдания

| Отговорка | Реальность |
|-----------|------------|
| «Слишком просто, чтобы тестировать» | Простой код тоже ломается. Тест занимает 30 секунд. |
| «Протестирую потом» | Тесты, написанные после, проходят сразу — и это ничего не доказывает. Ты не видел, как они падают, значит не доказал, что они могут поймать баг. |
| «Тот же результат, дух важнее ритуала» | Тесты-после отвечают «что делает код?», тесты-до — «что он должен делать?». Написанные после кода тесты смещены тем, что уже написано. |
| «Уже проверил вручную» | Ручная проверка не оставляет записи и не перезапускается при изменениях. «Сработало, когда я попробовал» ≠ исчерпывающе. |
| «Жалко удалять X часов работы» | Ошибка невозвратных затрат — время уже потрачено. Настоящий выбор: переписать с TDD (уверенность) или оставить и привинтить тесты после (баги). |
| «Оставлю как справочник, тесты напишу сначала» | Ты его адаптируешь. Это и есть тесты-после. Удалить — значит удалить. |
| «Сначала надо поэкспериментировать» | Хорошо. Выброси эксперимент, начни с TDD. |
| «Тест тяжело писать» | Слушай тест. Трудно тестировать = трудно пользоваться. Значит, дизайн плохой. |
| «TDD замедлит меня» | TDD и есть прагматичный путь: ловит баги до коммита, предотвращает регрессии, позволяет рефакторить без страха. |
| «В коде нет тестов» | Ты его улучшаешь. Добавь тесты к существующему коду. |

## Красные флаги — СТОП и начни заново

- код до теста
- тест после реализации
- тест проходит сразу
- не можешь объяснить, почему тест упал
- тесты «добавлю потом»
- «уже проверил вручную»
- «оставлю как справочник»
- «TDD догматичен, я прагматичен»
- «это особый случай, потому что...»

**Всё это означает: удали код. Начни заново с TDD.**

## Пример: исправление бага

**Баг:** принимается пустой email

**КРАСНЫЙ**
```typescript
test('отвергает пустой email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Укажите email');
});
```

**Проверка КРАСНОГО**
```bash
$ npm test
FAIL: expected 'Укажите email', got undefined
```

**ЗЕЛЁНЫЙ**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Укажите email' };
  }
  // ...
}
```

**Проверка ЗЕЛЁНОГО**
```bash
$ npm test
PASS
```

**РЕФАКТОРИНГ:** при необходимости вынеси валидацию нескольких полей в общую функцию.

## Чек-лист проверки

Прежде чем считать работу завершённой:

- [ ] У каждой новой функции/метода есть тест
- [ ] Ты видел, как каждый тест падает, до реализации
- [ ] Каждый тест падал по ожидаемой причине (нет функциональности, не опечатка)
- [ ] Написан минимальный код для прохождения каждого теста
- [ ] Все тесты проходят
- [ ] Вывод чистый (без ошибок и предупреждений)
- [ ] Тесты используют реальный код (моки только если неизбежно)
- [ ] Краевые случаи и ошибки покрыты

Не можешь отметить все пункты? Ты пропустил TDD. Начни заново.

## Когда застрял

| Проблема | Решение |
|----------|---------|
| Не знаешь, как тестировать | Напиши желаемый API. Сначала напиши проверку (assert). Спроси у человека. |
| Тест слишком сложный | Значит, дизайн слишком сложный. Упрости интерфейс. |
| Приходится мокать всё | Код слишком связан. Используй внедрение зависимостей. |
| Огромная подготовка теста | Вынеси в вспомогательные функции. Всё ещё сложно? Упрости дизайн. |

## Связь с отладкой

Найден баг? Напиши падающий тест, воспроизводящий его. Пройди цикл TDD. Тест докажет исправление и защитит от регрессии.

Никогда не исправляй баги без теста.

## Финальное правило

```
Продакшен-код → тест существует и падал первым
Иначе → это не TDD
```

Никаких исключений без разрешения человека.
