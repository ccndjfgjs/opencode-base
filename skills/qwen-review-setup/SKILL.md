# Настройка второго ревьюера — руками агента

Этот скилл про **настройку ревьюера агентом**, а не про проверку кода.
Сама проверка кода — скилл `qwen-review`; окружение Qwen Code из его
README — тоже там.

## Как это работает

Человек не жмёт кнопки в окне: он говорит агенту «настрой ревьюера» или
«настрой тройное ревью», и агент делает всё сам. Окно программы отдало
настройку скиллу: на вкладке opencode остались статус и кнопки «Проверить
изменения», «Проверить доступность» и «Настроить через скилл».

## Когда брать

- «настрой ревьюера», «настрой тройное ревью», «поменяй провайдера или
  модель», «проверь, какие модели отвечают».
- Ревьюер отвечает ошибкой **401** — найти причину по ключу.
- На вкладке пустая панель тройного ревью, а человек попросил голосование.

## Когда не брать

- **Нужна сама проверка кода** — бери `qwen-review`, не этот.
- **Нет провайдеров в настройках opencode.** Ревьюер выбирает модель из
  уже подключённых провайдеров opencode. Если их нет — сначала человек
  подключает провайдера в opencode, потом настройка. Об этом сказать.
- **Провайдер не в формате OpenAI.** Программа сама скажет, что он не
  подходит. Подставлять наугад чужой адрес нельзя.

## Порядок настройки (весь — руками агента)

Выполняй по порядку, каждую команду смотри и объясняй человеку словами:

```
python tools/dbapp/qwen_review.py status          # что готово, чего не хватает
python tools/dbapp/qwen_review.py providers       # провайдеры opencode и их модели
python tools/dbapp/qwen_review.py check-models <провайдер>   # живые модели (реальные запросы!)
python tools/dbapp/qwen_review.py choose <провайдер> <модель>
python tools/dbapp/qwen_review.py deploy          # развернуть Qwen Code, если ещё нет
python tools/dbapp/qwen_review.py install         # включить отметку ревьюера
python tools/dbapp/qwen_review.py review <папка>  # проверить — скилл qwen-review
```

### Выбор провайдера и модели — критерий, а не вкус

1. `providers` даёт всех подключённых. Модель берём **только из списка
   этого провайдера**, а не выдуманную.
2. `check-models <провайдер>` показывает живые модели **✔**, мёртвые
   **✘** (401/404 — окончательно) и **?** (429/таймаут — НЕ отказ, это
   лимит, повторить позже). Потолок 120 моделей за прогон, кэш сутки.
3. **Выбирай провайдера с наибольшим числом живых (✔) моделей.** Это
   объективный критерий: у кого больше живых моделей, тот надёжнее.
4. **Ничья по числу живых — единственный случай спросить человека.**
   Не гадай и не тяни жребий: скажи «у обоих по две живые модели, кто
   нравится больше?» и дай выбор.
5. **Каждая проверка — реальный запрос за счёт провайдера** (промпт из
   одного символа, один токен, потолок 120, кэш сутки). Не проверяй все
   провайдеры подряд из любопытства: проверь кандидатов, а не весь список.
6. `choose <провайдер> <модель>` пишет выбор в `qwen-review-data` рядом
   с настройками opencode. Ключ в файл не пишется — в окружение процесса.
7. Проверь, что всё готово: `status` должен ответить «Готово», а ряд
   `check-models` показать выбранную модель ✔.

### Развёртывание и включение

- `deploy` ставит Qwen Code в свою папку программы (npm без `-g`), если
  ещё нет. Нужен Node.js 22+.
- `install` включает отметку ревьюера, `remove` — снимает.

### Регистрация Qwen как агента opencode

Определение агента живёт в `tools/agents/retsenzent-qwen.md` и едет в
настройки opencode **тем же механизмом, что двенадцать основных агентов**
(при установке/обновлении базы). После настройки ревьюер доступен как
агент `@retsenzent-qwen` — ряд основных агентов. Если `status` пишет
«нет файла агента» — значит база старая, сначала обнови её; руками файл
не копируй.

## Режимы ревьюера

| id | Имя | Что делает | Что требует |
|---|---|---|---|
| `once` | Одна проверка | Ревьюер один раз смотрит `git diff` и присылает замечания. Возражений и раундов нет. | галочка qwen-review; одна модель ревьюера |
| `debate` | Спор | Ревьюер присылает замечания, основной агент возражает, ревьюер отвечает — до заданного числа раундов. Решает человек. | галочка qwen-review; переключатель «спор»; две стороны; раунды 1–5 |
| `vote` | Тройное ревью | **Три** модели из панели смотрят один diff, программа сводит замечания: что заметили две-три — сверху, чьё мнение одно — отдельно. | галочка qwen-review; панель из трёх слотов; у каждого слота свой провайдер и модель |

Режимы задаются `review <папка> --mode once|debate|vote`. Вызовы без
`--mode` работают как раньше: есть `--reply` — спор, нет —
одна проверка. **Источник истины — MODES в `tools/dbapp/qwen_review.py`.**
Таблица — пересказ для человека; при расхождении правь код, а не скилл.

### ⛔ Запрет: «спор» + «тройное ревью» вместе

**`debate` и `vote` несовместимы: включать их одновременно нельзя, и в
кли командной строке их подача вместе обязана кончиться отказом.**
Причины: спор — обмен возражениями двух сторон; тройное ревью — одна
сборка diff на три голоса. В споре три модели собирали бы каждый раунд
заново и голосование не стало бы голосованием. Программа отказывает
словами: «Спор с тройным ревью не совмещается… Убери --reply или выбери
режим debate». Эту ошибку не обходи и не «чини» сам — она сделана
намеренно.

## Панель тройного ревью

Когда человек просит «настрой тройное ревью» — заполни панель тремя
слотами по тем же критериям выбора (максимум живых, ничья — спросить):

```
python tools/dbapp/qwen_review.py panel show          # текущие слоты
python tools/dbapp/qwen_review.py panel set <1|2|3> <провайдер> <модель>
python tools/dbapp/qwen_review.py panel clear         # очистить всё
```

- У каждого слота **свой провайдер и своя модель** — так мнения
  правда от трёх разных моделей, а не от трёх копий одной. Если живых
  провайдеров меньше трёх, слоты можно повторить, но скажи человеку
  про это словами: голосование тогда слабее.
- После заполнения `panel show` должен показать панель, а `status` —
  «Готово». Проверь.
- Пустая панель при попытке `review --mode vote` — отказ словами:
  «Скажи агенту: настрой тройное ревью». Это подсказка человеку, а не
  сбой: агент (это ты) услышит её и заполнит панель.
- **Свобода рук для агента:** в настройке не согласуй каждый шаг.
  Спрашивай только две вещи — ничейный выбор провайдера (и слота, если
  счёт совпадает) и перед развёртыванием Qwen Code, если оно нужно,
  потому что это установка внешнего пакета на компьютер человека.

## Разбор 401

401 — провайдер отверг ключ. `provider_key_info` в
`tools/dbapp/qwen_providers.py` возвращает и ключ, и словами источник.
Порядок получения жёсткий (сверху сильнее):

1. **переменная окружения** по имени из поля `env` провайдера;
2. **ссылка `{env:ИМЯ}`** в `apiKey` настроек opencode;
3. **литерал** ключа прямо в `opencode.jsonc`.

Проверь, что ключ **от того провайдера, куда ходишь**: в этом проекте
под провайдером `dahl` лежал ключ от Alibaba — и 401 был честный,
«ключ есть, но не тот». Источник получается словами («переменная
окружения X» или «литерал в opencode.jsonc»). Приоритет: переменная
окружения сильнее литерала; старый литерал в файле молча игнорируется,
если в окружении стоит новый.

## Безопасность ключей

- **Полный ключ никогда не печатается** — ни в ответ, ни в журнал, ни
  в окно, ни в файлы. Наружу только маска: первые 4 символа и длина
  (`sk-1… (длина 51)`); короткие ключи (до 8 символов) не показываются
  даже частично.
- **Между слотом и ключом — строгая пара.** У каждого провайдера ключ
  свой; 401 цитирует присланный ключ, и маска обязана быть его, а не
  соседнего провайдера. Общая маска `mask_known_keys` вычищает и чужой
  ключ, если его вписали в имя модели руками. Не печатай ключ из вывода
  команд — программа уже вычистила его своей маской.
- **Граница маски — наш код.** Qwen Code живёт в своей папке
  (`qwen-review-data\qwen-home`), и он может оставить ключ в СВОИХ
  файлах. Это его территория. Проверяй чужие файлы глазами, если
  подозреваешь утечку.
- Программа называет **имя переменной**, а не её значение.

## Частые ошибки

- «В файле ключ есть, а 401» → приоритет источников: в окружении стоит
  другая переменная, и она сильнее. Раздел «Разбор 401».
- `check-models` ответил «?» на всё → это не отказ: 429 или таймаут.
  Повтори позже, по одному провайдеру.
- Кнопка «Проверить доступность» гаснет на время проверки → так и задумано.
- Повторный прогон не бьёт по API → кэш суток ещё жив.
- «Спор с тройным ревью не совмещается» → это намеренный отказ, не обходи
  и не «чини»: спор и голосование — разные режимы, вместе они не ходят.
